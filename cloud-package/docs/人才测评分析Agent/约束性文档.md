# 人才测评分析 Agent 约束性文档

> 版本：v1.0  
> 日期：2026-09-28  
> 适用范围：P-21～P-26 以及对应后端服务、Agent、数据库和接口

## 1. 文档目的

本文档定义开发、联调、测试和上线时不可违反的规则。它的作用不是描述建议方案，而是作为代码评审、接口评审、数据库迁移评审和验收的硬性门槛。

特别约束：第三项要求已经明确为“开发实施文档分四批实现代码”。因此，任何实现都必须按开发实施文档的四批边界推进，不允许一次性编写跨越四批的大段代码；发生上下文压缩或人员交接时，必须以本目录文档和批次检查点恢复工作。

后端启动门槛：需求、API、DB、状态机、数据字典、验收条件六项必须全部对齐并完成评审记录后，才允许开始后端业务实现。

## 2. 原型和后端一致性约束

1. P-21～P-26 原型中的每个按钮、筛选、页签、抽屉、确认框、状态、错误态和展示数据，都必须有后端数据来源或接口契约。
2. 前端不得长期保留只在 HTML 中生效的假操作。`data-toast-message` 只能作为原型占位，进入联调后必须替换为真实接口调用。
3. 原型操作没有对应后端接口、数据库字段、权限规则和测试用例时，该功能不得标记为完成。
4. 页面展示的统计数字、题目列表、任务进度、异常数、报告分数和证据内容不得由前端硬编码。
5. 接口缺失时必须在接口矩阵中登记为未完成，不得通过前端隐藏按钮掩盖缺口。

## 3. 四批代码交付约束

### 第一批：P-21/P-22

只实现题库、能力维度、组卷和试卷发布。不得在本批实现在线作答、报告生成和画像同步。

完成条件：题目版本、审核、启停、固定/随机组卷、配额校验、题目快照和发布冻结可用。

### 第二批：P-23/P-24

只实现测评任务、候选人分配、服务端时间、作答、保存、恢复、提交和自动交卷。不得绕过已发布试卷快照直接读取题库当前版本。

完成条件：任务生命周期和在线作答链路可独立运行，重复提交、断点恢复、超时和答案版本冲突有测试。

### 第三批：P-25/P-26

第三批仍是一个批次，但必须按三个独立检查点交付：

- **3A 监控 + 异常 + 人工复核**：事件上报、规则配置、异常摘要、事件复核、人工待办和审计。
- **3B 评分 + 证据**：确定性评分、AI 辅助评分、评分快照和证据生成；不依赖 3C。
- **3C 报告 + 发布 + 画像补偿**：报告、报告复核、发布、`outbox_event` 画像同步和失败补偿。

完成条件：3A、3B、3C 各自有独立迁移/测试/验收记录；客观分、AI 建议分、人工最终分严格分离；报告发布前的证据和人工确认校验可阻断发布。

### 第四批：P-21～P-26 全链路

只实现跨批联调、权限、审计、错误态、幂等、限流、性能、安全、故障恢复和验收，不在本批偷偷增加新的业务范围。

完成条件：六个原型页面从真实 API 加载数据并完成一条创建题目到发布报告的完整链路。

### 批次隔离规则

- 每批代码必须有独立的迁移、测试和验收记录。
- 前一批未通过验收，不得开始后一批的核心业务代码。
- 每个批次结束时必须保存 OpenAPI 快照、数据库迁移版本和测试报告。
- 单文件超过 400 行时必须拆分；单个函数不得同时负责权限、事务、状态机和外部调用。
- 上下文压缩后，先读取本文件、开发实施文档对应批次和接口矩阵，再继续写代码。

## 4. 数据不可违反约束

1. 已发布题目版本、试卷版本、候选人题目快照、评分和报告不得覆盖或物理删除；TBL-36 `assessment_answer` 仅保存当前答案，允许在 Attempt 版本校验通过后更新，不保存无限历史答案。
2. 发布试卷必须冻结题目版本、题目顺序、分值、客观评分规则、能力维度及维度权重快照、组卷规则、配额规则和随机种子；已发布 Paper 的 `version_no` 是本次测评完整评分上下文版本。
3. 任何会影响评分结果的变化，即使题目内容不变，也必须创建新的 Paper 版本；不得原地修改已发布 Paper。
4. 随机卷必须为每个候选人保存实际题目快照，不能在作答时重新随机。
- 除已冻结表级字段例外外，每张业务表必须按 `tenant_id` 隔离；组织范围数据必须二次校验 `org_id`。TBL-36 `assessment_answer` 按表级字段定义不包含 `tenant_id`，通过关联 Attempt 执行权限和数据范围校验。
5. 所有写操作必须记录操作者、角色、租户、组织、资源、旧状态、新状态、请求 ID、幂等键和时间。
6. 任何状态变更必须由服务端状态机执行，前端不得直接传入任意目标状态。
7. `assessment_task.duration_min` 是任务时长配置；开始作答时必须写入 `assessment_attempt.duration_min_snapshot` 和 `deadline_at_snapshot`，作答期间不得回读可变任务配置计算截止时间。
8. `assessment_task_candidate` 是 P-23 候选人分配、进度和提醒状态的权威来源；不得用前端计算结果替代。
9. `assessment_monitor_rule` 是 P-25 监控规则和版本的权威来源；规则修改必须产生新版本或明确的行版本变更。
10. `assessment_event_review` 专门记录异常事件复核，不得用报告复核表的 `report_id` 语义替代。
11. `assessment_notification` 记录通知/提醒投递状态；通知、画像同步及其他跨事务业务事件统一写 `outbox_event`，不得新增测评专用 outbox。

### 4.1 Agent 状态机约束

Agent 运行状态只有：

```text
queued -> running -> waiting_human -> running -> success
异常 -> failed
```

`resumed` 只能表示恢复动作，禁止作为持久化状态；`completed` 不得作为最终状态。重试是执行动作/次数，不是状态。人工等待和恢复必须复用 `agent_interrupt`。

## 5. 评分和报告约束

1. 单选、多选、量表等客观题只能由确定性规则引擎评分。
2. 多选题默认全对得分，错选或漏选不得按模型判断部分正确；若评分规则变更，必须创建新的 Paper 版本，不能修改原 Paper 的评分规则。
3. 简答题 AI 只能生成 `subjective_ai_score`、理由、置信度和证据候选，不得写入 `final_score`。
4. 人工改分必须填写理由，并保留旧分、新分、复核人和复核时间。
5. 报告中的优势、短板、风险和建议都必须引用至少一个稳定 `evidence_id`。
6. `unsupported`、缺题目版本、缺答案版本、缺分数快照或来源不一致的证据不得进入已发布报告。
7. 报告发布前必须满足：客观题完成、主观题有建议或人工分、待确认项为零、高影响结论已确认、证据完整。
8. 发布动作必须生成不可覆盖的发布快照和审计记录；新报告只能生成新版本并将旧版标记为 `superseded`。
9. 评分唯一键必须是 `(attempt_id, rule_version, score_key)`；`assessment_score.rule_version` 必须等于该 Attempt 创建时绑定的 Paper `version_no`。`report_id` 允许为空，报告生成后再关联，禁止使用 `report_id` 作为评分唯一键。

## 6. 作答和时间约束

1. 服务端时间是开始、截止、自动交卷和超时判断的唯一依据。
2. 客户端时间只能用于展示和诊断，不能决定成绩有效性。
3. 答案保存必须携带版本号；旧版本写入必须返回冲突，不得覆盖新版本。
4. 提交作答必须幂等；重复提交只返回同一结果，不重复写入评分任务 Outbox 事件。
5. 候选人只能访问本人有权限的任务、作答实例和已发布报告。
6. 任务撤回、归档和已提交作答不能通过普通编辑接口恢复或覆盖，必须走明确的状态操作接口。

### 6.1 Attempt 契约冻结约束

1. Attempt 状态只能是 `not_started`、`in_progress`、`submitted`、`auto_submitted`、`cancelled`。只允许 `not_started -> in_progress -> submitted`、`in_progress -> auto_submitted`、`not_started / in_progress -> cancelled`；`submitted`、`auto_submitted`、`cancelled` 为终态，不得新增状态。
2. API-131 首次请求创建 Attempt。若存在 `in_progress` Attempt，必须返回已有 Attempt，不创建新 Attempt，不增加 `attempt_count`；已有终态 Attempt 时按 `attempt_limit` 判断是否允许下一次。
3. API-131 必须使用服务端时间，并将 Candidate 行锁、次数校验、`attempt_no` 生成、`attempt_count` 递增、`paper_snapshot` 生成、`duration_min_snapshot`、`deadline_at_snapshot` 和 Attempt 创建放在同一事务中。`attempt_count` 是次数限制的权威依据。
4. `assessment_attempt.answer_version` 初始值为 `0`。客户端首次提交 `answer_version=0`，服务端校验成功后将当前 `assessment_answer.answer_version` 写为 `1`，并将 Attempt 版本更新为 `1`；后续提交版本 `N` 成功后更新同一答案记录为 `N+1`。冲突返回 `40902`，不得覆盖并发更新，不创建历史 answer 行。
5. `paper_snapshot` 必须在 API-131 创建时从 TBL-33 固化；Attempt 同时在业务语义上绑定创建时任务关联的已发布 Paper `version_no`。API-133 只能读取该快照，不能实时读取题库或当前最新 Paper 内容。本轮不新增 Attempt 字段或改变当前快照结构，具体承载方式留待后续实现阶段。
6. API-138 只有 `confirm=true` 才能正式提交，且只能执行 `in_progress -> submitted`。提交必须锁定 Attempt、校验 `in_progress`、冻结答案、写提交时间、更新 Candidate，并与评分任务 Outbox 事件写入处于同一数据库事务。评分 Outbox 固定为 `event_type=assessment.score.requested`、`aggregate_type=assessment_attempt`，payload 严格包含 `attempt_id`、`task_id`、`tenant_id`、`answer_version`，幂等键为 `attempt_id:score:v{answer_version}`；本轮不修改该 payload。后续评分流程必须通过 Attempt 创建时绑定的 Paper `version_no` 取得 `assessment_score.rule_version`，不得读取当前最新 Paper。成功响应严格只返回 `attempt_id`、`status`、`submitted_at`、`outbox_event_id`，不得返回 `agent_task_id`。事务成功后返回提交成功，Outbox 写入失败则整体回滚。相同 `Idempotency-Key` 重复提交返回首次成功结果；不同 `Idempotency-Key` 提交已为 `submitted` 的 Attempt 返回 `40902`。主动提交必须幂等。超时 Worker 以 `server_now >= deadline_at_snapshot` 独立触发 `in_progress -> auto_submitted`，并复用主动提交的处理原则；`submit_after_deadline` 仅作为事件类型，不参与 API-138 状态转换。
7. API-139 中 `Idempotency-Key` 是 HTTP 请求级幂等，`client_event_id` 是客户端事件级幂等；二者不一致不视为冲突。唯一作用域固定为 `tenant_id + attempt_id + client_event_id`，不同 `Idempotency-Key` 携带相同事件标识时返回首次 `event_id`。`client_event_id` 为 VARCHAR(64) NOT NULL。
8. Candidate 联动不得新增字段：API-131 成功开始时设置 `assignment_status=started`、`attempt_count+1`、`progress=0`，`deadline_at` 保持任务截止时间；API-134 只更新 `progress`，其他 Candidate 字段不变；API-138 设置 `assignment_status=submitted`、`progress=100`；自动交卷设置 `assignment_status=submitted`、`progress` 按最终答案计算；`attempt_count` 不变且 `deadline_at` 不变。各操作与对应 Attempt 写入处于同一事务边界。
9. TBL-37 必须包含 `client_event_id` VARCHAR(64) NOT NULL，唯一约束为 `uk_attempt_client_event(tenant_id, attempt_id, client_event_id)`。重复事件不创建新事件，返回首次创建的 `event_id`，不产生重复副作用。
10. TBL-37 字段严格只有 13 个：`id` BIGINT UNSIGNED PK NOT NULL、`tenant_id` BIGINT UNSIGNED NOT NULL、`attempt_id` BIGINT UNSIGNED NOT NULL、`client_event_id` VARCHAR(64) NOT NULL、`event_type` VARCHAR(32) NOT NULL、`occurred_at` DATETIME(3) NOT NULL、`received_at` DATETIME(3) NOT NULL、`duration_ms` INT UNSIGNED NULL、`metadata_summary` JSON NOT NULL、`severity` VARCHAR(16) NOT NULL、`review_status` VARCHAR(24) NOT NULL、`reviewed_by` BIGINT UNSIGNED NULL、`reviewed_at` DATETIME(3) NULL。所有字段均无数据库默认值，不使用 `CURRENT_TIMESTAMP`，禁止新增公共字段、`server_received_at`、`event_status`、`event_payload` 或其他事件业务字段；不创建物理 ForeignKey。
11. TBL-37 仅允许唯一约束 `uk_attempt_client_event(tenant_id, attempt_id, client_event_id)` 和普通索引 `idx_attempt_event_received(attempt_id, received_at, event_type)`，不得创建 `(attempt_id, occurred_at, event_type)` 索引。`event_type` 允许 `visibility_hidden`、`paste`、`idle`、`refresh`、`submit_after_deadline`、`device_change`；`severity` 允许 `low`、`medium`、`high`、`critical`，服务端映射为 `refresh=low`、`idle=low`、`visibility_hidden=medium`、`paste=medium`、`device_change=high`、`submit_after_deadline=critical`；`review_status` 允许 `unreviewed`、`reviewed`、`escalated`，API-139 创建时固定为 `unreviewed`。API-139 成功响应严格为 `{"event_id": "123456"}`。

12. TBL-35 `assessment_attempt` 严格使用表级定义的 15 个字段，表级定义优先于公共字段默认规则；不得增加 `org_id`、`created_at`、`created_by`、`updated_at`、`updated_by`、`row_version`、`deleted_at` 或其他字段。
13. TBL-35 仅允许唯一约束 `uk_attempt_task_user_no(task_id, user_id, attempt_no)` 和普通索引 `idx_attempt_task_status_saved(task_id, status, last_saved_at)`；不得创建条件唯一索引、`is_active`、`active_flag` 或其他状态辅助字段。`(task_id, user_id, status)` 仅作为查询优化建议。
14. 同一 `task_id + user_id` 同时只能存在一个 `status=in_progress` 的 Attempt。API-131 必须先锁定对应 `assessment_task_candidate` 行，在同一事务中查询现有 `in_progress` Attempt；存在则返回已有 Attempt，不存在才创建新 Attempt。该规则由服务层事务保证，不由数据库条件唯一约束保证。

15. TBL-36 `assessment_answer` 严格使用 12 个字段：`id`、`attempt_id`、`paper_question_id`、`answer_version`、`answer`、`answered_at`、`objective_score`、`subjective_ai_score`、`final_score`、`score_source`、`review_status`、`review_comment`；不增加 `tenant_id` 或其他公共字段。唯一约束为 `uk_attempt_question_answer(attempt_id, paper_question_id)`，不创建重复普通索引；`attempt_id`、`paper_question_id` 不建立物理 ForeignKey。

## 7. 监控、隐私和合规约束

1. 监控服务只记录、聚合和提示事件，不直接扣分、不取消成绩、不生成确定性的作弊结论。
2. `paste` 事件只保存发生时间、题目、内容长度等摘要，不保存剪贴板原文。
3. 不默认采集摄像头、麦克风、屏幕录像或生物特征数据。
4. 事件报告使用“待核查”“异常摘要”“需要人工确认”等措辞，不使用未经人工确认的“作弊”结论。
5. 发送给模型的内容必须脱敏，只包含评分所需的题干摘要、作答摘要、评分量表和必要上下文。
6. PDF 导出、报告查看、证据查看属于敏感数据读取，必须做权限检查和导出审计。

## 8. 权限约束

| 角色 | 允许范围 |
| --- | --- |
| `ADM` | 系统管理和全局配置，按租户授权范围访问 |
| `HR` | 题库、组卷、任务、监控、报告复核和发布，受组织范围限制 |

权限判断必须同时检查：认证身份、角色、租户、组织、资源归属、资源状态和字段级敏感权限。不能只在前端隐藏按钮。

## 9. Agent 运行约束

1. 复用现有 `agent_task`、`agent_step`、`agent_interrupt`，不得新增第二套状态机。
2. `business_key=assessment_attempt:{attempt_id}` 用于评分任务幂等。
3. Agent 节点必须记录输入摘要、输出摘要、状态、耗时、重试次数、规则版本和 trace_id。
4. 模型网关超时、限流或异常时，只重试可安全重试的节点；客观评分不得重复产生不同结果。
5. 人工复核通过 `agent_interrupt` 暂停和恢复，恢复时从最后一个成功节点继续。
6. 画像同步失败不回滚已发布报告，必须进入补偿队列并可重试、可观测、可审计。

## 10. 接口兼容约束

1. 成功响应必须使用统一结构，成功判定为 `code == 0`。
2. ID 必须以字符串返回，禁止把雪花 ID 直接作为 JSON number。
3. 写接口必须定义幂等行为；不能因为重试产生重复任务、重复报告或重复通知。
4. 已发布 API 的字段不能无版本地改名、改类型或改变枚举含义。
5. 错误码必须稳定，前端只能依赖错误码和结构化字段，不得依赖中文 message 做分支。
6. 新增原型操作前，必须先补数据库字段、接口、权限、测试和覆盖矩阵。
7. 一个接口只能对应一个 API 编号；测评接口从 `API-096` 起连续编号至 `API-159`，不得合并接口或为了压缩编号跳过实际接口。
8. 接口实现必须与 API 目录中的请求、响应、权限、幂等、数据表和原型映射一致。

## 10.1 页面状态约束

1. 通用状态统一为 `loading / empty / error / forbidden / conflict`。
2. 页面只需覆盖适用的通用状态；不适用状态不得为了凑覆盖率强行增加。
3. `reconnecting`、`expired`、`submitted`、`auto_submitted`、`evidence_incomplete`、`waiting_review`、`published`、`superseded` 等属于业务状态，必须在对应页面单独定义，不能冒充通用状态。

## 11. 测试和验收约束

每个批次至少包含：

- 正常流程测试。
- 空数据和加载态测试。
- 参数错误、资源不存在和服务降级测试。
- 权限、租户和组织越权测试。
- 并发版本冲突和幂等测试。
- 状态机非法流转测试。
- 审计、trace_id 和敏感字段脱敏测试。

第四批必须额外完成：

1. P-21～P-26 原型操作覆盖率 100%。
2. 从题目创建、审核、组卷、发布、任务、作答、提交、监控、评分、复核到报告发布的端到端回归。
3. 报告证据引用可以反向定位到题目版本、答案版本和评分快照。
4. 发生模型超时、数据库短暂不可用、队列积压、画像同步失败时，系统状态仍然可解释、可恢复。
5. 四批代码分别有独立的检查点，不允许以“最后整体联调”替代批次验收。
