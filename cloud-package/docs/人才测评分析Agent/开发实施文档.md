# 人才测评分析 Agent 开发实施文档

> 版本：v1.0  
> 日期：2026-09-28  
> 实现策略：四批代码交付，批次内小步提交和验证

## 1. 实施目标

本实施文档把 P-21～P-26 原型转成可运行后端能力。原则是：原型中出现的展示数据、筛选、按钮、抽屉、确认框、状态和异常态，都必须有明确的后端接口、数据模型、权限规则和测试；不能出现“前端已经有按钮，后端没有接口”的情况。

截至本版本分析，`backend/app/routers` 中没有独立的 assessment 路由，因此本功能按新业务域建设，并复用现有认证、统一响应、组织范围、Agent、审计和 AI 日志能力。

### 1.1 后端开发启动条件

在开始任何后端业务实现前，以下六项必须全部对齐并由评审记录确认：

1. 需求分析文档；
2. 接口设计文档及 API-096~API-159 编号清单；
3. 数据库设计文档；
4. Agent 和页面业务状态机；
5. 数据字典；
6. 各批次验收条件。

任一项未对齐，只能继续做文档或契约测试准备，不得开始后端业务代码。

本次文档评审对齐结果：需求 ✓、API ✓、DB ✓、状态机 ✓、数据字典 ✓、验收条件 ✓。当前仍未启动后端业务实现。

#### Attempt 契约冻结后的实施前置

Attempt 实施不得早于以下数据表顺序：

```text
TBL-32 -> TBL-33 -> TBL-35 -> TBL-36 -> TBL-37
```

API-131 必须在一个事务中完成 Candidate 行锁、`attempt_limit` 校验、`attempt_no` 生成、`attempt_count` 递增、TBL-33 题目快照固化和 TBL-35 Attempt 创建；Attempt 业务上绑定创建时任务关联的已发布 Paper `version_no`，该版本用于后续 `assessment_score.rule_version`。已有 `in_progress` Attempt 时只返回已有记录。API-138 只能执行 `in_progress -> submitted`；其成功响应严格返回 `attempt_id`、`status`、`submitted_at`、`outbox_event_id`，不返回 `agent_task_id`。评分 Outbox 固定为 `event_type=assessment.score.requested`、`aggregate_type=assessment_attempt`，payload 为 `attempt_id`、`task_id`、`tenant_id`、`answer_version`，幂等键为 `attempt_id:score:v{answer_version}`；本轮不修改该 payload，后续评分流程必须从 Attempt 创建时的 Paper 版本取得 `rule_version`。相同 `Idempotency-Key` 重复提交返回首次成功结果，不同 `Idempotency-Key` 提交已为 `submitted` 的 Attempt 返回 `40902`。主动提交和超时 Worker 必须通过 Attempt 行锁/状态条件实现单一生效结果，并复用答案冻结、评分任务 Outbox 事件写入和 Candidate 更新逻辑；`submit_after_deadline` 仅作为事件类型，不参与 API-138 状态转换。

TBL-37 必须包含 `client_event_id` VARCHAR(64) NOT NULL，并建立唯一约束 `uk_attempt_client_event(tenant_id, attempt_id, client_event_id)`。重复事件返回首次 `event_id`，不创建新事件且不产生重复副作用。Candidate 联动固定为：API-131 设置 `assignment_status=started`、`attempt_count+1`、`progress=0`；API-134 只更新 `progress`；API-138 设置 `assignment_status=submitted`、`progress=100`；自动交卷设置 `assignment_status=submitted`、`progress` 按最终答案计算；`deadline_at` 按冻结规则保持不变。不得新增 Candidate 字段。

TBL-37 完整字段严格为 13 个：`id` BIGINT UNSIGNED PK NOT NULL、`tenant_id` BIGINT UNSIGNED NOT NULL、`attempt_id` BIGINT UNSIGNED NOT NULL、`client_event_id` VARCHAR(64) NOT NULL、`event_type` VARCHAR(32) NOT NULL、`occurred_at` DATETIME(3) NOT NULL、`received_at` DATETIME(3) NOT NULL、`duration_ms` INT UNSIGNED NULL、`metadata_summary` JSON NOT NULL、`severity` VARCHAR(16) NOT NULL、`review_status` VARCHAR(24) NOT NULL、`reviewed_by` BIGINT UNSIGNED NULL、`reviewed_at` DATETIME(3) NULL。所有字段均无数据库默认值，由应用服务显式赋值。唯一约束为 `uk_attempt_client_event(tenant_id, attempt_id, client_event_id)`，普通索引为 `idx_attempt_event_received(attempt_id, received_at, event_type)`，不创建 `(attempt_id, occurred_at, event_type)` 索引；不增加公共字段、`server_received_at`、`event_status` 或 `event_payload`，不创建物理 ForeignKey。`event_type` 使用 `visibility_hidden`、`paste`、`idle`、`refresh`、`submit_after_deadline`、`device_change`；`severity` 使用 `low`、`medium`、`high`、`critical`，服务端映射为 `refresh=low`、`idle=low`、`visibility_hidden=medium`、`paste=medium`、`device_change=high`、`submit_after_deadline=critical`；`review_status` 使用 `unreviewed`、`reviewed`、`escalated`，API-139 创建时固定为 `unreviewed`，成功响应严格只返回 `event_id`。

TBL-35 实施冻结为 15 个字段，不套用公共字段 Mixin，不增加 `org_id`、`created_at`、`created_by`、`updated_at`、`updated_by`、`row_version`、`deleted_at` 或其他字段。Migration 只创建 `uk_attempt_task_user_no(task_id, user_id, attempt_no)` 和普通索引 `idx_attempt_task_status_saved(task_id, status, last_saved_at)`，不创建条件唯一索引；`(task_id, user_id, status)` 仅保留为查询优化建议。活跃 Attempt 唯一性由 Attempt Service 锁定 Candidate 行并在同一事务内查询、返回或创建 `in_progress` Attempt 保证。

TBL-36 实施冻结为 12 个字段：`id`、`attempt_id`、`paper_question_id`、`answer_version`、`answer`、`answered_at`、`objective_score`、`subjective_ai_score`、`final_score`、`score_source`、`review_status`、`review_comment`；不增加 `tenant_id` 或其他公共字段。答案仅保存当前记录，不保存无限历史；客户端首次提交版本 `0`，成功后当前答案版本为 `1`，后续按 `N -> N+1` 更新同一记录。唯一约束为 `uk_attempt_question_answer(attempt_id, paper_question_id)`，不创建重复普通索引；`attempt_id`、`paper_question_id` 不建立物理 ForeignKey。

### 第三批：监控、评分 Agent 和能力报告

第三批仍是一个批次，但拆成 3A、3B、3C 三个独立检查点。3B 必须在没有 3C 的情况下独立运行；3C 只能消费已确认的评分和证据快照。

#### 3A：监控、异常和人工复核

**代码范围：**

- TBL-37、TBL-42、TBL-44、TBL-45、TBL-46 的迁移、模型、schema、DAO。
- `MonitoringService`：事件上报、规则版本、阈值聚合、时间线、异常摘要、事件复核、人工待办和摘要导出。
- `assessment_event_review` 专门记录异常事件复核；`agent_interrupt` 只负责 Agent 人工等待和恢复。

**独立测试和验收：**

1. P-25 的事件列表、异常筛选、事件详情、核查、待办、升级、规则配置和导出均有 API、权限、审计和失败恢复测试。
2. 监控只记录和提示，不扣分、不取消成绩、不生成确定性作弊结论。
3. 规则按 `assessment_monitor_rule` 版本化；重复事件和通知按幂等键去重。

#### 3B：评分和证据

**代码范围：**

- TBL-36、TBL-38、TBL-39 的评分、证据迁移、模型、schema、DAO。
- `AssessmentScoreGraph` 的 `validate_attempt`、客观评分、维度聚合、主观题 AI 建议和证据生成节点。
- 评分唯一键为 `(attempt_id, rule_version, score_key)`；其中 `rule_version` 必须等于 Attempt 创建时绑定的 Paper `version_no`，`report_id` 可为空，报告生成后再关联。

**独立测试和验收：**

1. 客观题规则评分可重复，AI 只能写建议分、理由和证据候选，不写最终分。
2. 每条报告候选结论至少能绑定一个有效 `evidence_id`，证据可回溯题目版本、答案版本和规则版本。
3. 评分和证据可以在没有报告发布表写入的情况下完成并查询；模型失败不影响客观评分。

#### 3C：报告、发布和画像补偿

**代码范围：**

- TBL-40、TBL-41 和 TBL-46 的报告、复核、发布、审计和事件投递。
- `ReportService`：报告详情、评分明细、版本历史、证据引用、复核、发布、PDF 导出、Agent 运行和回放。
- 发布事务统一写 `outbox_event`；画像同步在事务外消费，失败进入可重试补偿，不回滚已发布报告。

**独立测试和验收：**

1. 证据缺失、主观题未复核或高影响结论未确认时，发布接口必须拒绝。
2. 发布生成不可覆盖快照；重复发布不生成重复报告版本或重复画像事件。
3. P-26 的报告、证据、复核、发布、导出、Agent 运行和回放均有 API、权限、审计和失败恢复测试。

**第三批总检查点：**

- 验证 Agent 在 `waiting_human` 中断后通过 `agent_interrupt` 恢复到 `running`，最终以 `success` 或 `failed` 结束。
- 验证 3B 不依赖 3C；验证模型超时不会阻断客观题结果，并进入重试/人工队列。
- 验证报告发布和画像同步失败的状态语义不混淆，画像失败只产生 `outbox_event` 补偿。

### 第四批：全链路联调和生产级加固

**页面范围：P-21～P-26 全部页面**

**代码范围：**

- 六个页面与后端 API 的联调适配。
- 统一权限、租户隔离、组织范围和适用的通用状态：`loading / empty / error / forbidden / conflict`；不适用状态不强行增加，业务状态单独定义。
- 审计、trace_id、幂等、限流、分页、导出权限、敏感字段脱敏。
- Agent 重试、任务积压、人工待办超时、画像同步补偿和回放。
- OpenAPI、接口契约测试、性能测试、安全测试、迁移回滚演练。

**必须覆盖的原型状态：**

- 页面按适用性覆盖 `loading / empty / error / forbidden / conflict`；例如 P-21 要覆盖 loading、empty、error、forbidden，P-22 要覆盖 loading、empty、conflict、forbidden。
- P-23 另测 `withdrawn`、`archived`；P-24 另测 `reconnecting`、`expired`、`submitted`、`auto_submitted`；P-25 另测 `异常待核查`；P-26 另测 `evidence_incomplete`、`waiting_review`、`published`、`superseded`。

**验收门槛：**

1. 原型覆盖矩阵 100% 映射到接口和测试用例。
2. 普通列表接口 P95 小于 500ms，不包含模型调用。
3. 答案保存并发测试不发生版本覆盖。
4. 跨租户、跨组织、员工查看他人报告等越权用例全部失败。
5. 从创建题目到发布报告再到人才画像同步完成一条完整回归链路。

## 4. 防止长代码和上下文压缩导致问题的开发规则

1. 每批只实现一个页面闭环或一组紧耦合服务，不在同一批新增无关功能。
2. 每完成一个 DAO、Service 或 Router 文件，立即运行对应测试，不累计到批次末尾。
3. 单文件优先控制在 400 行以内；超过后按领域拆分，不用超长函数承载多个状态流转。
4. 每批开始前先读取本批接口清单、数据库字段和验收项；每批结束后写入变更摘要和未完成项。
5. 代码实现必须以接口文档为唯一契约，页面新增操作必须先补接口矩阵和测试，再写代码。
6. 每批完成后保留可运行状态，禁止依赖后续批次的未实现接口才能启动服务。
7. 发生上下文压缩、会话中断或开发人员交接时，以本目录需求、架构、数据库、数据字典、接口、开发实施和约束文档及批次检查点恢复，不凭记忆补代码。

## 5. 统一完成定义

每个批次必须同时满足：

- 数据库迁移可执行、可回滚。
- Model、Schema、DAO、Service、Router 和权限检查完整。
- 接口响应符合现有 `{code, message, data, page, trace_id}` 约定。
- 原型操作与接口映射完整。
- 正常、空、加载、错误、冲突、无权限状态有测试。
- 幂等、审计、日志和失败恢复已验证。
- 代码通过格式化、静态检查和该批次测试。
