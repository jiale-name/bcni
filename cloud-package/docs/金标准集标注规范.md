# 金标准集标注规范（一期 · N0 交付物）

| 项目 | 内容 |
| --- | --- |
| 文档性质 | **标注作业指导书**（发甲方 HR 专家 / 业务专家使用） |
| 上游依据 | 需求分析文档 v1.3 **§12.1 N0 ⑪** · **§12.5 数据与语料** · **§5 IDX-01 / IDX-02** · **§6.2 一期核心指标** |
| 配套工具 | `backend/scripts/goldset.py`（模板生成 / 质检 / 脱敏） |
| 标注规模 | 简历标注集 **≥200 份** · 查询-人才集 **≥50 条** |
| 责任方 | **甲方** HR 专家 + 业务专家（需求 §12.5：乙方无业务判断力，D-11） |
| 工作量估算 | 简历 **6~8 人天**（约 1.5~2 人天/50 份）· 查询集 **2~3 人天** · 合计 **8~11 人天** |

> 🔴 **为什么必须在 N0 阶段启动**：需求 §12.1 的「前置强依赖」写明 ——
> *N6 的准确率评估完全依赖金标准集，而金标准集需甲方标注 → 必须在 N0 阶段启动，不能等到 N6*。
> 这是 N0 里唯一「人力即工期」的任务，晚一周启动，验收就晚一周。

## 一、这批数据用来干什么

一期有 **3 项核心指标**，其中 **2 项只能靠本规范产出的金标准集验证**：

| 指标 | 口径 | 验证方式 |
| --- | --- | --- |
| **IDX-02** 简历字段级准确率 | **≥ 95%**（图片/扫描件单列口径） | 本规范的**简历标注集 ≥200 份** |
| **IDX-01** 语义检索 Recall@10 | **≥ 85%** | 本规范的**查询-人才集 ≥50 条** |
| IDX-04 向量检索延迟 | P95 ≤ 500ms @100 万向量 / 200 并发 | 压测报告（与本集无关） |

**金标准集是「唯一验证手段」**（需求 §12.5 原文）—— 没有它，准确率指标既无法证明达标，也无法在未达标时定位到具体字段。

## 二、标注流程（五步）

```text
① 生成模板  →  ② 读本规范  →  ③ 逐份标注  →  ④ 每 50 份质检  →  ⑤ 脱敏交付
```

| 步骤 | 操作 | 命令 / 说明 |
| :-: | --- | --- |
| ① | 生成模板 | `cd backend && .venv/Scripts/python.exe scripts/goldset.py build` |
| ② | **读本规范第 三、四 节** | 尤其「缺失怎么标」—— 这是最容易错、也最难返工的一项 |
| ③ | 用 Excel / WPS 填写 | 字段列留空 = 还没标；确实没有的信息填 `缺失` |
| ④ | 每完成约 50 份跑一次质检 | `.venv/Scripts/python.exe scripts/goldset.py validate` |
| ⑤ | 全部完成后脱敏 | `.venv/Scripts/python.exe scripts/goldset.py seal` |

**④ 是关键**：口径错误在标注**现场**发现，代价是改 3 行；等 200 份标完再发现，代价是重标 200 份。

## 三、简历标注集：逐字段口径

模板共 21 列：**8 列管理信息 + 13 列待标字段**。管理信息中 `resume_id` / `file_name` / `file_type` 由工具生成，**不要改**；`status` / `annotator` / `annotated_at` / `remark` 由标注人填写。

### 3.1 管理列（标注人需填的部分）

| 列 | 怎么填 |
| --- | --- |
| `status` | `pending` 未开始 → `annotating` 标注中 → `done` 已完成 → `reviewed` 已复核。**只有 `done` / `reviewed` 的行参与评估**。 |
| `annotator` | 标注人姓名（用于追溯与工作量核算） |
| `annotated_at` | 完成日期，如 `2026-09-25` |
| `remark` | 任何需要说明的情况（如「简历只写年龄未写出生年月」）。⚠️ **不要在这里写手机号等联系方式**（脱敏时不会处理本列） |

`file_type` 取值含义：

| 取值 | 含义 |
| --- | --- |
| `text_pdf` | 有文本层的 PDF（可直接复制文字） |
| `text_docx` | Word 文档 |
| `text_other` | 其它文本格式 |
| `scan_image` | 图片件（jpg / png，截图或拍照） |
| `scan_pdf` | 扫描件 PDF（无文本层，必须 OCR） |

> 🔴 `scan_image` 与 `scan_pdf` 会被**单独统计**（IDX-02 要求「图片件单列口径」）。
> 判断方法：用 PDF 阅读器**选中文字**——选不中就说明没有文本层，应标 `scan_pdf`。
> 模板默认按 20% 均匀铺入图片件（40 份），请按实际文件修正。

### 3.2 字段列（13 项）

| 列 | 中文名 | 分组 | 落库位置 | 填法与要点 |
| --- | --- | --- | --- | --- |
| `name` | 姓名 | 基础信息 | TBL-11 `talent_base.name` | 照抄简历姓名；有英文名时以中文名为主，英文名写进 `remark` |
| `gender` | 性别 | 基础信息 | `talent_base.gender` | 只填 `男` / `女`；未写或无法判断填 `缺失`。🔴 **不得按姓名推测** |
| `birth_date` | 出生年月 | 基础信息 | `talent_base.birth_date` | 填 `YYYY-MM`（如 `1995-03`）；简历只写年龄时填 `Age:28`，并在 `remark` 写基准日期。⚠️ 年龄与出生年月**不可互换**，脚本分列统计 |
| `education_level` | 学历 | 教育经历 | `talent_base.education_level` | **必须用字典值**：`high_school` / `college` / `bachelor` / `master` / `doctor`（填中文名也可，脚本会归一；填字典外的取值**会被质检拦下**） |
| `school` | 院校 | 教育经历 | `talent_base.school` | **全称**（`华中科技大学` 而非 `华科`）；多学历时填最高学历对应院校 |
| `major` | 专业 | 教育经历 | `talent_base.major` | 最高学历的专业全称 |
| `work_years` | 工作年限 | 工作经历 | `talent_base.work_years` | **整数年**（`5` 而非 `五年` / `5年`）；简历只给起止时间时按「最早入职 → 当前」折算，并在 `remark` 写明依据 |
| `work_exp` | 任职经历 | 工作经历 | TBL-12 `talent_work_exp` | 多值用 `\|` 分隔，段内用 `;` 分隔六项：`公司全称;部门;职位;起始;结束;是否在职`。按**时间倒序**。公司取主体全称，外包/驻场写进 `remark` |
| `project_exp` | 项目经历 | 工作经历 | TBL-13 `talent_project_exp` | 多值 `\|`；段内五项：`项目名称;角色;起始;结束;技术栈(逗号分隔)` |
| `skill` | 技能 | 技能与证书 | TBL-14 `talent_skill` | 多值 `\|`；同一技能取**最通用写法**（`PostgreSQL` 而非 `pg`） |
| `cert` | 证书 | 技能与证书 | TBL-15 `talent_cert` | 证书全称，多值 `\|`。⚠️ 「英语四级」这类**无证书载体的等级**不算证书，写进 `remark` |
| `phone` | 手机号 | 联系方式 | TBL-11 `phone_enc` / `phone_hash` | 🔴 **明文列**，只存甲方本地；交付前必须 `seal`。未提供则填 `缺失` |
| `email` | 邮箱 | 联系方式 | `talent_base.email_enc` | 同上；多个邮箱填最常联系的那个，其余写 `remark` |

**多值与子字段的分隔符（务必统一）**

| 场景 | 分隔符 | 示例 |
| --- | :-: | --- |
| 列表字段的**多个元素** | `\|` | `Python\|Milvus\|RAG` |
| 单个元素的**多个子字段** | `;` | `某某科技有限公司;数据平台部;高级算法工程师;2020-07;now;是` |
| 技术栈等**子字段内部**的并列项 | `,` | `Python,LangChain,Milvus` |

### 3.3 🔴 缺失怎么标（最易错、最难返工）

| 情况 | 正确做法 | 错误做法 |
| --- | --- | --- |
| 简历上**确实没有**这项信息 | 填 `缺失` | 留空（与「还没标」混为一谈） |
| 还没看到 / 还没标 | **留空** | 填 `缺失`（会被当成真值不存在） |
| 简历信息模糊难以判断 | 填 `缺失` + `remark` 说明 | 猜一个填上（会污染金标准） |
| 系统将来输出时 | 必须**显式标记缺失**，不得编造 | 编造具体值（会被计入「编造率」并判错） |

> **为什么这么严**：需求 F-3.2 明确要求「缺失字段显式标记**而非编造**」。
> 如果标注时用留空表示缺失，评估脚本就无法区分「真值缺失」与「标注人忘了」，
> 而「系统编造」这一最严重的错误恰好会以「正确」的形式混进准确率里。

## 四、查询-人才集：填写口径

共 10 列，50 条。**这是 IDX-01（Recall@10 ≥85%）的分母。**

| 列 | 怎么填 |
| --- | --- |
| `query_id` | 工具生成（`Q-001`…），不要改 |
| `query_text` | **自然语言查询**，像真人对话那样写，不要写成关键词堆砌。例：`找擅长数字化转型、3 年以上 AI 项目经验的骨干` |
| `intent` | 建议取值 `skill` 技能型 / `experience` 经历型 / `education` 教育型 / `composite` 综合型 / `negative` 否定排除型 |
| `expected_resume_ids` | 🔴 **期望被召回的人才**，填简历集的 `resume_id`（如 `RS-0007`），多条用 `\|` 分隔。**不得引用不存在的编号** |
| `top_k` | 固定 `10`（指标就叫 Recall@**10**） |
| `hard_filters` | 硬性筛选条件（如 `学历≥本科`）；没有则留空 |
| `notes` | 该查询的意图说明、边界约定（如「不考虑实习经历」） |
| `status` / `annotator` / `annotated_at` | 同简历集 |

**写法示例**

| query_text | intent | expected_resume_ids | notes |
| --- | --- | --- | --- |
| 找擅长数字化转型、3 年以上 AI 项目经验的骨干 | composite | `RS-0003\|RS-0012\|RS-0088` | 「骨干」指有独立负责项目经验 |
| 有没有做过金融风控相关项目的人 | experience | `RS-0045` | 只看正式项目，实习不算 |
| 985 硕士，计算机相关专业 | education | `RS-0007\|RS-0061` | 院校以最高学历为准 |

**三条质量要求**

1. **覆盖真实业务场景**（不是为测试而造的怪句子）—— 检索效果最终要在真实提问上兑现；
2. **期望结果是「应该被召回的人」，不是「只召回这些人」** —— Recall 只看有没有漏，不看有没有多（多出的人由后续精排解决）；
3. **同一语义不要写多条**（会被质检判为重复并提示合并）—— 重复条目会重复计入平均，放大该语义的权重。

## 五、准确率怎么算（分母口径）

> ⚠️ 需求原文只写了「字段级准确率 ≥95%」，**未定义分母**。本节把口径**定稿一次**，N6 评估直接复用 ——
> 否则同一批数据可以算出 78% 也能算出 96%。

| 口径 | 定义 | 用途 |
| --- | --- | --- |
| **主口径** | `正确字段数 / 已标注字段数`（分母**只含真值存在的格子**） | ✅ **验收判定用这一档** |
| 辅助口径 | `完全匹配份数 / 总份数`（整份 13 字段全对才算对） | 仅作观察，❌ 不用于验收 |
| **编造率** | 真值缺失却被系统填了值的格子数 / 真值缺失的格子数 | 单列统计（F-3.2「不得编造」） |
| **图片件口径** | 在 `file_type ∈ {scan_image, scan_pdf}` 子集上单独计算主口径 | 单列统计（IDX-02 要求） |
| 查询集口径 | `Recall@10 = 前 10 条中命中期望人才的比例`，按查询取平均 | IDX-01 |

**比对规则**

- 真值 `缺失` → 系统也必须显式标记缺失，**输出任何具体值都判错**（并计入编造率）；
- 真值有值 → 系统输出**归一化后相等**才判对（大小写、全半角、空白差异不算错）；
- 列表字段（任职/项目/技能/证书）→ 按**集合**比对，**顺序不计**；多出或漏掉的元素各计一次错；
- 学历 → 统一归一化到字典码再比对；
- 联系方式 → **不比对明文**，比对盐化 SHA256（故交付版本必须已 `seal`）。

> 主口径为什么要「只把真值存在的格子进分母」：一份信息量很少的简历（没写证书、没写邮箱）
> 如果把这些「本来就没有」的字段算进分母，会因**简历本身信息少**而被判成「解析不准」——
> 那测的是简历，不是系统。

## 六、质检规则（`goldset.py validate`）

质检在标注**现场**拦住口径错误。规则分三级：❌ 错误（必须修）/ ⚠️ 告警（建议核对）/ ℹ️ 提示。

| 级别 | 编号 | 检查内容 |
| :-: | :-: | --- |
| ❌ | `F-001~003` | 文件不存在 / 缺必需列 / 编码无法解码（Excel 需存成 **CSV UTF-8**，勿存 GBK） |
| ❌ | `R-001` | 简历集不足 200 份 |
| ❌ | `R-002` / `R-003` | `resume_id` 重复 / 为空 |
| ❌ | `R-010` / `R-011` | `file_type` / `status` 出现非法取值 |
| ⚠️ | `R-020` | 尚无任何行标记 `done`（进度提示） |
| ⚠️ | `R-021` | `status=done` 的行里仍有空字段（漏填，或该填 `缺失`） |
| ⚠️ | `R-022` | 已完成但未填 `annotator` |
| ⚠️ | `R-030` | 已完成行的某字段填充率过低 |
| ⚠️ | `R-031` | 图片/扫描件样本为 0（IDX-02 单列口径无法评估） |
| ❌ | `Q-001` | 查询集不足 50 条 |
| ❌ | `Q-002` | `query_id` 重复 |
| ⚠️ | `Q-003` | 查询文本完全重复（会重复计入 Recall 平均） |
| ⚠️ | `Q-004` | `intent` 取值未登记 |
| ❌ | `Q-005` / `Q-006` | 已开始的查询缺 `query_text` / 缺 `expected_resume_ids` |
| ❌ | `Q-007` | 期望人才引用了**简历集中不存在**的 `resume_id`（常见于编号补零位数不一致） |
| ℹ️ | `Q-008` | `top_k` 不是 10 |
| ⚠️ | `Q-009` | 查询集尚未开始标注（进度提示） |

> 说明：`pending` 的行**不参与完整性检查**——「还没标」不等于「标错了」，
> 否则模板刚生成时就会刷出一屏假错误，真正的问题反而被淹掉。

## 七、工具命令速查

```bash
cd backend

# 生成模板（默认 200 份简历 + 50 条查询，图片件占 20%）
.venv/Scripts/python.exe scripts/goldset.py build

# 调整规模 / 图片件比例（数量不得低于需求下限，否则直接报错）
.venv/Scripts/python.exe scripts/goldset.py build --count 220 --image-ratio 0.25

# 质检（只读，不改标注文件）；加 --report 会额外写 CHECK_REPORT.md
.venv/Scripts/python.exe scripts/goldset.py validate --report

# 只看进度
.venv/Scripts/python.exe scripts/goldset.py status

# 脱敏：明文联系方式 → 盐化哈希，产出 sealed/resume_annotations_sealed.csv
.venv/Scripts/python.exe scripts/goldset.py seal
```

⚠️ `build` **默认不覆盖**已存在的文件（标注是人工资产）；确实要重来需显式加 `--force`。

## 八、🔴 个人信息与交付红线

1. **本标注集含真实个人信息，属甲方内部资产** —— 禁止提交到任何代码仓库、云盘、外部协作工具。
2. **联系方式不得以明文交付乙方** —— 交付前必须跑 `goldset.py seal`，把 `phone` / `email` 明文列替换为 `phone_hash` / `email_hash`。
3. **盐（`CONTACT_HASH_SALT`）是密钥，不是数据** —— ❌ 不随标注集交付；乙方侧由部署配置提供。盐一经使用**不可更换**（换盐会让已入库哈希全部失效）。
4. **`remark` 列不会被自动脱敏** —— 请勿在其中手写手机号 / 邮箱。
5. **脱敏后请抽查**：确认交付版本中不含明文手机号 / 邮箱。

## 九、常见错误速查（FAQ）

| 疑问 | 答案 |
| --- | --- |
| 简历里写了「五年工作经验」，填 `五年` 吗？ | ❌ 填整数 `5`。系统抽取的也是整数，口径不一致会导致该字段全错 |
| 简历只写了年龄 28 岁，没有出生年月 | 填 `Age:28`，并在 `remark` 写基准日期。**不要**自行折算成出生年份 |
| 某人在两家公司都待过，`work_exp` 怎么写？ | `公司A;部门;职位;2020-07;2022-06;否\|公司B;部门;职位;2022-07;now;是`（时间倒序） |
| 技能写了 `Python、Java`，用逗号还是竖线？ | 用 `\|`：`Python\|Java`（逗号是子字段内部的分隔符） |
| 学历写「本科」，可以吗？ | 可以，脚本会归一化成 `bachelor`；但**建议直接写字典值**，减少归一歧义 |
| 查询集里期望人才我想不到具体是谁 | 换一条你想得清楚的查询。`expected_resume_ids` 为空会导致该条无法计算 Recall |
| 标注到一半发现前面的口径错了 | 立即改口径**并在 `remark` 标注**，然后**重跑质检**定位受影响的行；口径变更需同步通知所有标注人 |
| 图片件看不清内容 | 填 `缺失` 并在 `remark` 写「图片模糊」，**不要猜** |
