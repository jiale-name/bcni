## 三、需人工执行的处置清单

**1. `reranker` bge-reranker-v2-m3 精排延迟**（🔴 阻塞项）

- 现状：Reranker 服务未监听：http://127.0.0.1:9997 无进程在听（3 种端点形状均连接失败）
- 处置：① 启动 Reranker 服务并确认端口在听：`netstat -ano | findstr :9997` 应见 LISTENING；② 装载 `bge-reranker-v2-m3`（TEI 常见 9997；Infinity 9997；Xinference 9997 + `/v1`）；③ 服务起来后重跑本探针即可转为 ✅ —— 本项只取决于「有没有起服务」，无需改代码。⚠️ 本机若设有 HTTP_PROXY，`curl http://127.0.0.1:9997/...` 会得到**代理伪造的 502**，排障请加 `--noproxy '*'` 才看到真相（探针已用 `trust_env=False` 规避）。

**2. `ocr` OCR / 文档解析依赖完整度**（🔴 阻塞项）

- 现状：仅有文档解析后端（openpyxl），**无 OCR 后端** —— 图片 / 扫描件简历无法解析（F-3.2 要求该口径单列统计，故必须有 OCR）
- 处置：装一个 OCR 后端：`pip install rapidocr-onnxruntime`（轻量推荐）或 `pip install paddleocr`（中文效果更好但更重）；注意 `pytesseract` / `easyocr` 还需额外的系统级依赖（Tesseract 二进制 / torch）。

**3. `cloud_channel` 云 GPU 通道 RTT**（⚪ 待办）

- 现状：未配置 CLOUD_LLM_BASE_URL，云通道未启用（D-19 一期默认全本地推理）
- 处置：本项**不影响一期开工**。仅当 N0 压测显示本地 bge-m3 / Reranker 吞吐不足、需要按 D-4 评估 Embedding 上云时，才配置 `CLOUD_LLM_BASE_URL` 并重跑本探针（须同时遵守 D-15 脱敏边界）。

**4. `milvus` Milvus（DS-2）**（🟡 降级）

- 现状：Milvus 2.6.1 连通 · 库 `talent_vec` 存在 · 现有 collection 0 个 —— **规模性能未验证**（§6.1① 要求 100 万向量下的延迟与 QPS，需灌数后复测）
- 处置：N0 仅能验证可用性。规模结论请在 N4 灌入 100 万向量后按 IDX-04 口径（P95 ≤ 500ms @ 100 万向量 / 200 并发）补测，勿用本项结果回答 IDX-04。

## 五、口径与局限（读数字前必看）

1. **单点探测 ≠ 压测结论**。本报告的 Redis 吞吐是**单连接串行**、Reranker 延迟是**单次调用**、云通道是 **TCP 建连 RTT**（不含 TLS / HTTP / 排队）。它们只用于建立基线量级，不能替代 IDX-04/05/11 的压测。
2. **Embedding 吞吐的「份/分钟」需换算**。报告给的是「单条文本 / 秒」，乘以 CL-3 分块方案的「单元数 / 份」才是需求 §6.1④ 的「份/分钟」；分块方案定稿后请在本报告追加一行换算结果。
3. **同一次运行内的数值不可横向比较**。首次调用含模型加载（bge-m3 在 CPU 上尤甚），本脚本通过逐轮换文本 + 多次采样尽量摊平；若数值明显异常，请加 `--embedding-rounds` 重跑。
4. **本报告不含任何凭据**。凭据只输出「已配置 / 未配置」；如发现报告中出现密钥，属渲染层缺陷，请立即反馈。
