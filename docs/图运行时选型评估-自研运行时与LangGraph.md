## 0. 结论摘要（TL;DR）

| 问题 | 结论 |
| --- | --- |
| 自研运行时在哪？ | `backend/app/agents/`，**5 个文件 1 195 行**：`graph.py`(514) / `checkpointer.py`(206) / `parse_graph.py`(318) / `registry.py`(93) / `__init__.py`(64)，另 83 个用例钉死 |
| 谁更好？ | **不是一个维度上的比较**：LangGraph 在「运行时能力」上明显更强（每步检查点 / 时间旅行 / 并行分支 / 流式 / 子图）；自研在「与本项目的契合度」上明显更强（**0 新增依赖、与六层架构和三条铁律零冲突、租户隔离天然正确、单事务原子**） |
| 切过去最大的坑？ | LangGraph **官方没有 MySQL 检查点实现**；社区包 `langgraph-checkpoint-mysql` 自建表（**绕过 Alembic**）、表内**无 `tenant_id`** → 同时撞上**铁律 7**（ORM+Alembic 唯一事实来源）与**租户隔离**两条红线 |
| 最关键的解法 | **切换 ≠ 必须用社区 MySQL 包**。实现自己的 `BaseCheckpointSaver` 适配器（落我们的表、带 `tenant_id`、走 Alembic、可分区）即可同时满足设计要求与铁律 —— 这是本评估最重要的技术结论 |
| 还有个被忽略的问题 | **当前状态本身就已是「技术偏离」**：ADR-2 / ADR-11 / D-2 都点名 LangGraph，而 **§6.5 技术偏离申报要点里没有这一条** → 无论切不切，**都要补申报**（见 §5） |
| **「现在不切」会不会逼着自研继续长功能？** | **不会**：把「LangGraph 有而自研没有」的能力收敛为四类（并行分支 / 子图 / 状态历史 / 流式），逐单元核对 **CU-14 ~ CU-17 —— 四类全部为「不需要」**（§9）→ **第 3 批需要新增的运行时能力 = 0**；唯一该补的**节点级检查点**属**横切增强**（崩溃恢复），不是新能力 |
| **会不会让未来切换更贵？** | **只要守住 §10 的 6 条原则就不会** —— 它们**不增加任何开发成本**（都是本来该守的纪律），却把切换面从「重写运行时 + 重写图」压到「只换装配层 + 自写 saver」 |
| 建议 | 一期**保留自研**并补两处增强；**CU-21（RAG 问答）开工前**按 §7 的三个触发条件重新决策 |

## 1. 现状盘点：自研运行时长什么样

### 1.1 文件与调用链

```text
routers/agent_router.py（API-90~95）
        │
services/agent_service.py   ← 15 处耦合（启动 / 恢复 / 重试 / 幂等 / 步骤落库 / 检查点）
        │   run_graph / resume_state / GraphOutcome
        ▼
agents/registry.py           task_type → GraphDefinition（唯一映射，F-A0.7 数据源）
        │
agents/parse_graph.py        8 个节点 + 3 条条件边 + 1 个中断点
        │
agents/graph.py              纯运行时（不碰 DB、不碰 HTTP ⇒ 用例全是 L1）
agents/checkpointer.py       落 agent_task.graph_state / current_node / status + agent_step + agent_interrupt
```

### 1.2 F-A0 七项能力的覆盖情况（**对照需求逐项**）

| 能力 | 自研实现 | 覆盖度 |
| --- | --- | :---: |
| F-A0.1 状态持久化 | `agent_task.graph_state`（JSON）+ `MySqlCheckpointer` | ✅ 但**粒度是 run 级**（见 §4.1） |
| F-A0.2 循环与分支 | `edges`（静态）+ `routers`（条件）+ `max_steps` 死循环兜底 | ✅ |
| F-A0.3 人工介入 | 节点返回 `InterruptRequest` → 立即挂起 → 落 `agent_interrupt` → API-94 恢复 | ✅ |
| F-A0.4 失败重试 | `RetryableNodeError` 按节点重试；`NodeError` 不重试 | ✅ |
| F-A0.5 步骤可观测 | 每节点一条 `agent_step`（输入 / 输出 / 耗时 / 错误） | ✅ |
| F-A0.6 幂等 | `agent_task.idempotent_key` + `idempotent_result`（40903 返回首次结果） | ✅ |
| F-A0.7 可视化配置 | `GraphDefinition.describe()` → 节点 / 边 / 中断点清单 | ✅ |

**83 个用例**（`test_agent_graph.py` 43 + `test_agent_flow.py` 40）已经把上述行为钉死 ——
这也是「替换成本」的量化单位：**这 83 条断言的可信度是当前最值钱的资产**。

### 1.3 与 LangGraph 的三处**有意不同**（切换时最容易被当成 bug 的地方）

| # | 本项目的做法 | LangGraph 的做法 | 谁更适合本项目 |
| :-: | --- | --- | --- |
| 1 | **挂起后只跑后继节点**：人工结论存 `state["__human__"][节点名]`，由后继节点读取 | **重放中断节点**：`interrupt()` 返回恢复值，但**它之前的代码会再执行一遍** | ⚠️ **本项目**：解析节点会写库、调模型，强制「节点纯函数」不现实 |
| 2 | 检查点 **run 级**（一次 run 结束写 1 次） | **每 super-step** 写一次 | ⚠️ **LangGraph**（这是自研的真实短板，见 §4.1） |
| 3 | `state` 是**普通 dict**（可 JSON 落 LONGTEXT，键名自由） | 需 `TypedDict` + reducer 声明 | ✅ 各有取舍：dict 灵活但无类型约束；TypedDict 有约束但**改状态结构要动 schema** |

> 🔴 第 1 条必须写进任何切换方案的风险清单：LangGraph 官方与社区文档**一致**强调
> 「`interrupt()` 之前的代码会跑两次，副作用必须幂等或移到 `interrupt()` 之后」。
> 当前 `field_review` 是**纯函数**（无副作用），所以现在切是无痛的；
> 但 **CU-14/15 的节点一旦在 interrupt 前写库，就会重复副作用**。

## 2. LangGraph 侧的事实（实测，非印象）

### 2.1 版本与依赖树

`langgraph` 当前 **1.2.12**（1.0 于 2025-10-22 GA，承诺 v1 线内不破坏兼容）。
引入它与 MySQL 检查点包，**实测会新增 24 个包**：

| 类别 | 包 |
| --- | --- |
| LangChain 系 | `langchain-core 1.6.4` · `langgraph-checkpoint 4.2.0` · `langgraph-prebuilt 1.1.0` · `langgraph-sdk 0.4.5` · `langsmith 0.14.0` · `langchain-protocol` |
| 检查点 | `langgraph-checkpoint-mysql 3.0.0`（**社区包**） |
| 🔴 **编译扩展（4 个）** | `ormsgpack`（Rust）· `xxhash`（C）· `zstandard`（C）· `uuid_utils`（Rust） |
| 网络与工具 | `httpx2` · `httpcore2` · `requests` · `requests-toolbelt` · `websockets` · `distro` · `sniffio` · `truststore` · `tenacity` · `jsonpatch` · `jsonpointer` · `charset-normalizer` |

两个需要单独点出来的：
- **`httpx2`**：本机测试目前会打 `StarletteDeprecationWarning: Using httpx with starlette.testclient is deprecated; install httpx2 instead`。
  装进 `httpx2` 后 **Starlette 的 `TestClient` 可能切到新实现** → 现有 **654 个用例的 HTTP 层行为需整体复核**。
- **4 个编译扩展**：源码在 PyPI 上都有 manylinux/win_amd64 wheel，但**信创环境（ARM64 / 麒麟 / 统信）**是否齐全，
  直接挂在 **Q-3 国产化清单**上 —— 这是本次评估里**唯一无法在本机验证**的风险。

### 2.2 检查点后端矩阵（**这条决定了切换的难度**）

| 后端 | 归属 | 备注 |
| --- | --- | --- |
| `InMemorySaver` | langgraph 核心 | 进程重启即丢，仅测试 |
| `SqliteSaver` | 官方包 | 本地单进程 |
| `PostgresSaver` | 官方包 | Q1 2026 达生产稳定 |
| `RedisSaver` | 官方包 | 低延迟 / TTL |
| `MongoDBSaver` | 生态包 | 1.3.0 起 |
| **MySQL** | ❌ **无官方实现** | 只有社区包 `langgraph-checkpoint-mysql` 3.0.0（MIT，个人维护，2026-01-23 发版，要求 MySQL ≥ 8.0.19 —— 本机 8.0.27 ✅，且提供**同步 `PyMySQLSaver`**，与我们的同步栈兼容） |

社区包的两个硬冲突（**这是本次评估最关键的发现**）：

1. **`checkpointer.setup()` 自己建表**（裸 DDL，在 Alembic 之外）
   → 直接违反**铁律 7「数据库唯一事实来源是 ORM 模型 + Alembic」**，
   而这些表的**分区 / 清理策略**也不在迁移链里（我们的 `ai_call_log` / `audit_log` 已经建立了按月分区那套）。
2. **检查点表里没有 `tenant_id`**
   → 违反「DAO 每个查询必须带 `tenant_id`」这条红线。
   跨租户隔离只能靠**应用层约定 `thread_id = f"{tenant_id}:{task_id}"`** ——
   而**约定不是保证**：任何一处直接 `invoke(thread_id="42")` 就能读到别人的图状态。

> ✅ **解法：不用社区包，自己实现 `BaseCheckpointSaver`**（`checkpointer.py` 的 docstring 早已预留了
> 这个可替换点）。落**我们自己的表**：带 `tenant_id`、由 Alembic 建表、按月分区、
> 复用现有 `MySqlCheckpointer` 的落库逻辑（`save` / `record_step` / `create_interrupt` 三个动作已是现成的）。
> 预估 200~300 行 + 1 条迁移 —— **这一步把「切换」从「违反两条铁律」变成「完全合规」**。
> 代价是：社区包解决的那部分（序列化格式、版本兼容）要自己维护。

### 2.3 HITL 语义的差异（引三处独立来源交叉验证）

| 环节 | 自研 | LangGraph |
| --- | --- | --- |
| 暂停 | 节点返回 `InterruptRequest`，运行时**立即挂起、不推进后继** | `interrupt(value)` 抛内部异常，图停机并写检查点 |
| 恢复 | `resume_state()` 写 `__human__` → `run_graph(start_node=后继节点)` | `invoke(Command(resume=值), config)` |
| 恢复时执行什么 | **只跑后继节点**（副作用只发生一次） | **重放中断节点本身**（`interrupt()` 之前的代码再跑一遍） |
| 待办载体 | `agent_interrupt` 表（**我们自己的**，API-93/94 契约不变） | interrupt payload（中性，**同样可以落 `agent_interrupt`**） |

**好消息**：LangGraph 的 interrupt 只负责「暂停 + 取值」，**待办表是我们自己的** ——
所以**API-90~95 的契约、`agent_step` 回放、`agent_interrupt` 三态（40902/40903）全都不需要改**。
替换面被限制在**运行时内部**，不会外溢到接口层。这是切换成本可控的根本原因。

| 维度 | 自研运行时 | LangGraph 1.2.12 | 谁赢 |
| --- | --- | --- | :---: |
| 交付形态 | 1 195 行自有代码，可读可改 | 24 个外部包 + 其升级节奏 | 自研 |
| 依赖风险 | **0 新增**（纯 stdlib + 现有栈） | +24 包，含 **4 个编译扩展** | 自研 |
| 信创可用性（Q-3） | 无新风险 | 4 个编译扩展的 ARM64 wheel 待验证 | 自研 |

## 4. 切换的六类真实代价（逐条量化）

### 4.1 数据面：检查点粒度是自研**最大的功能缺口**

实测确认：`_persist_outcome` 只在 `run_graph` **返回后**执行一次（`agent_service.py` 3 处调用点：
`start_task` / `retry_task` / `_resume`），每步回调 `_step_callback` **只写 `agent_step`、不写检查点**。

后果：一个跑了 8 个节点、在第 7 个节点崩溃的任务，**只能从头重跑**（当前跑得快所以不明显；
CU-14 接入 OCR + 模型抽取后，一次 run 从「毫秒」变成「分钟级」，这个问题就会显形）。

→ 这是**唯一一条「不切也该修」的项**，且改动很小：在 `on_step` 回调里顺带保存一次轻量检查点
（约 20 行 + 1 个用例）。

### 4.2 代码面

| 文件 | 行数 | 切换时 |
| --- | :-: | --- |
| `agents/graph.py` | 514 | 整体作废（换 LangGraph 运行时；但 `InterruptRequest` / `StepRecord` / `NodeContext` 的**设计**可以平移） |
| `agents/checkpointer.py` | 206 | **不废弃** —— 落库逻辑（save / record_step / create_interrupt）复用，外面套一层 `BaseCheckpointSaver` 适配器 |
| `agents/parse_graph.py` | 318 | 节点函数**逻辑不变**，签名从 `NodeContext` 改为 `(state, config)`；条件边函数基本可直接用 |
| `agents/registry.py` | 93 | 保留（它是业务侧职责，LangGraph 无对应物） |
| `agent_service.py` | 813（15 处耦合） | 改 `run_graph` / `resume_state` 的调用点为 `invoke` / `Command(resume=)`；`_persist_outcome` 退化为「只写任务状态 + 待办」 |
| `test_agent_graph.py` | 43 例 | **重写**（断言对象变了） |
| `test_agent_flow.py` | 40 例 | 大多保留（端点级，API 契约不变） |

### 4.3 依赖面

+24 包、4 个编译扩展、`httpx2`（可能改变 `TestClient` 行为，需复核 654 个用例的 HTTP 层）。
**一期是信创项目**，这条要挂在 Q-3 上。

### 4.4 数据结构面

`agent_task.graph_state` 的 JSON 结构会变成 LangGraph 的 `channel_values` 形态；
**在途任务需要重跑**（一期开发环境无生产数据 → 实际可忽略，但**上线后切换的成本完全不同**）。
**结论：要切就现在切，越晚越贵。**

### 4.5 事务面

LangGraph 的 saver 走**自己的连接**（`from_conn_string`），与业务 `Session` 不共享事务 →
「业务回滚了、检查点留下了」或反之。自研运行时今天是**同一 Session 一次 commit**。
若自写 saver，可以强制它复用同一个 `Session`，这一条可以守住。

### 4.6 语义面

「重放中断节点」这个语义要**逐节点审计**现有的与环境中的副作用（见 §1.3）。
当前 `field_review` 是纯函数 → 无痛；但这是**每新增一张图都要重新审一遍**的长期成本。

## 5. 🔴 上游文档符合性：不切**也是一种偏离**（本评估最容易被忽略的一条）

LangGraph 在**上游文档里是被点名写死的**：

| 文档 | 位置 | 原文（节选） |
| --- | --- | --- |
| 架构设计 | **ADR-2** | 「**决策**：Dify 管模型网关 + Prompt 管理；**LangGraph 管有状态 Agent**」 |
| 架构设计 | **ADR-11** | 「Agent 在需复核/审批节点调用 `interrupt`，落 `agent_interrupt` 待办；人工在工作台处理后续跑（Checkpointer 从最后成功节点恢复）」 |
| 架构设计 | §2.1 选型表 | 「服务：Agent 编排 / **LangGraph** / 原生 Checkpointer + interrupt，支撑 HITL」 |
| 需求分析 | **D-2**（技术环境策略） | 「**新增**：PgSQL、Vanna.ai、**LangGraph**」 |
| 数据流图 | **SQ-7** | 「LangGraph `interrupt → resume` 的状态持久化」 |
| 接口设计 | API-94 / API-39 | 「**LangGraph 从 `interrupt` 点恢复执行**」「解析异步执行（Redis 队列 + LangGraph）」 |

**但要注意 ADR-11 的实际要求是「行为」而不是「库」**：interrupt → 落待办 → 从最后成功节点恢复 ——
**自研运行时已经逐条满足**。所以本项偏离的性质是：

> **组件选型偏离**（用了语义对齐的自研实现），**不是功能偏离**。
> 功能点 F-A0.1~A0.7、接口 API-90~95 全部按契约交付。

**处置建议（无论最续选哪个方案都要做）**：
在评审文档 **§6.5 一期技术偏离申报要点**补一行（待用户确认后正式写入）：

## 9. CU-14 ~ CU-17 的「四类能力」核查 🔴（回答「现在不切会不会逼着自研继续长功能」）

> 方案 A 的风险只有一条：**如果接下来的编码单元不停要求运行时提供新能力，
> 那么「暂时不切」就在事实上变成了「在自研上重造 LangGraph」** —— 那才是真正的沉没成本。
> 所以必须逐个单元核对，而不是靠印象。
>
> 核查方法：把「LangGraph 有而自研没有」的能力**收敛为四类**（并行分支 / 子图 / 状态历史 / 流式），
> 然后看 CU-14 ~ CU-17 是否真的要用到它们。

### 9.1 逐单元核查表

| 单元 | 功能 | 是否需要<br/>并行分支 | 是否需要<br/>子图 | 是否需要<br/>状态历史 | 是否需要<br/>流式 | 结论 |
| :-: | --- | :-: | :-: | :-: | :-: | --- |
| **CU-14** | 简历批量导入 + 任务进度（SSE） | ❌ | ❌ | ❌ | ❌（**不是 token 流**，见 9.2） | 队列 + 外层循环；SSE 读 TBL-20/21 推**作业级**事件 |
| **CU-15** | 字段抽取 + 字典归一 + 置信度 | ❌ | ❌ | ❌ | ❌ | **已被 `parse_graph` 现有 8 节点覆盖**（`ocr` / `extract_fields` / `normalize_fields` / `score_confidence`） |
| **CU-16** | 分层复核漏斗 + 复核工作台 | ❌ | ❌ | ❌ | ❌ | **人工介入 F-A0.3 已覆盖**（`interrupt` + `agent_interrupt`）；批量复核 = Service 循环 + `conflicted[]` 部分成功语义（接口 §6.1） |
| **CU-17** | 受控标签词表 + AI 选标签闭环 | ❌ | ❌ | ❌ | ❌ | **循环 + 条件边 F-A0.2 已覆盖**；「AI 建议 → 管理员审核 → 入库」是**业务状态机**，不是图能力 |

### 9.2 四条取证（为什么「不需要」是结论而不是印象）

**① 并行分支 —— DF-2 的「逐文件解析」是「任务级并行」，不是「图内 fan-out」**

DF-2 的画法与外层语义是「**逐文件**更新进度（TBL-21）」「**单个文件失败不阻塞整批**」；
SM-2 更把这条写成红线：**`部分失败` 与 `失败` 平级，都从 `解析中` 直接到达**，不允许把「有 1 个文件失败」判成整批失败。

→ 这意味着 **N 个文件 = N 个互相独立的执行单元**，实现方式是「外层循环 / 队列消费 + 每个文件一次 `run_graph`」，
**既不需要 `Send` fan-out，也不需要 merge 聚合点**（没有「汇总后再决策」的环节，只有「逐文件独立完成」）。
LangGraph 的 `Send` 解决的是「**同一张图内**分叉再汇合」，而 DF-2 的语义根本不存在汇合点。

⚠️ **但要登记一个边界**：**若将来要求「同一批 100 份必须在图内并行 fan-out 后再做批内去重/合并」，
那才是第一个真正的并行需求** —— 最可能出现的单元是 **CU-19（查重与合并，F-3.5）** 或 **CU-20（混合召回，F-3.6）**。
→ 故 **§7 的监控点应从「CU-21 开工前」提前到「CU-18 / CU-19 开工时」**（比原判断更保守）。

**② 流式 —— API-39 的 SSE 是「作业级进度流」，真正的 token 流只有 API-63**

接口文档 §5.1 把两个 SSE 接口并列列出，事件类型**完全不同**：

| 接口 | 用途 | 事件类型 | 数据源 | 属于谁 |
| --- | --- | --- | --- | --- |
| **API-39** `/talent/import/{task_id}/progress` | 导入解析进度 | `queued` / `progress` / `done`（+ `error`） | **TBL-20 / TBL-21** 的状态与计数 | **CU-14** |
| **API-63** `/talent/ask` | 档案 RAG 问答 | `meta` / **`delta`** / `citation` / `refusal` / `done` / `error` | LLM token 流 | **CU-21** |

→ **CU-14 的 SSE 不需要运行时支持流式**：它的数据源是**数据库里的计数**，
实现方式是「独立线程 / 协程轮询 TBL-20/21 → 组装 SSE 帧」，与图运行时**完全无关**（F-A0.5 的步骤可观测已足够支撑）。
真正的 token 级 `delta` 只出现在 **API-63**（CU-21）—— 那也正是触发条件 ② 的落点。

**③ 状态历史 —— F-3.10 是「业务数据版本」，不是「图状态时间旅行」**

**这是最容易误判的一处**，必须写清楚：

| | LangGraph 的 `get_state_history` | 本项目的 F-3.10（CU-22） |
| --- | --- | --- |
| 记录对象 | **图的状态快照**（每一步的 `state`） | **档案字段的变更**（变更前值 / 变更后值 / 来源 / 操作人 / 任务 ID） |
| 载体 | LangGraph 检查点表 | **TBL-22**（`change_source` 区分 AI 解析 / 人工复核 / 合并 / 重解析） |
| 业务用途 | 调试 / 回放 / 时间旅行 | **合规留痕 + 字段级变更链 + 时间点回溯 + 合并解绑回滚**（不可篡改、留存 ≥12 个月） |
| 混淆的后果 | 会误判为「F-3.10 需要 LangGraph」→ 得出「必须切」的错误结论 | 同一份需求其实用**业务表**实现更准确（图状态里**没有**「操作人」「来源」这些业务语义） |

→ **F-3.10 与图运行时无关**，它的实现是「字段级 change log + 快照还原」，与 CU-22 自研即可。
（顺带说明：**节点级检查点**补上以后，自研**也**有了「按步恢复」，只是**没有**暴露时间旅行 API —— 而本项目**没有任何需求**要这个 API。）

**④ 子图 —— CU-14 ~ CU-17 全是单图**

四个单元都是「单张图 + 线性/条件流转 + 人工中断」，不存在「图内调用另一张图」的嵌套需求
（子图的真实落点是**多智能体协同**，即触发条件 ③）。

### 9.3 结论

> **第 3 批（CU-14 ~ CU-17）需要新增的运行时能力 = 0。**
>
> 现有的 F-A0 七项能力（状态持久化 / 循环与分支 / 人工介入 / 失败重试 / 步骤可观测 / 幂等 / 可视化配置）
> 已经够用；唯一该补的是**节点级检查点**，而它属于**横切增强**（把「崩了能恢复」从 run 级做到节点级），
> **不是**「为了追 LangGraph 而补的能力」。
>
> 更关键的一点：**它让检查点数据模型更靠近 LangGraph**（每步一个检查点），
> 所以补它是在**降低**而非抬高未来的切换成本 —— 这与「在自研上堆功能会变贵」的直觉相反，需要单独说明。

## 10. 迁移成本控制：6 条原则（**最小可丢弃面**）

> 既然一期不切，就必须保证「今天写得更顺手」不会变成「将来切得更贵」。
> 下面 6 条**不增加任何开发成本**（它们本来就是这个项目该守的纪律），
> 但能把未来的切换面从「**重写运行时 + 重写图**」压到「**只换装配层 + 自写一个 saver**」。

| # | 原则 | 具体做法 | 它买到了什么 |
| :-: | --- | --- | --- |
| 1 | **图定义保持「声明式」** | `GraphDefinition` 只描述节点、边、中断点；**不得**持有运行时对象或连接 | 换运行时只需重写「装配层」，**图本身不动** |
| 2 | **节点函数只用 `NodeContext` 暴露的接口** | 只用 `human_input()` / `last_decide` 等；**不得** import `graph` 模块内部符号 | 节点函数是切换时**唯一需要改签名**的面 → 把它收窄到 2~3 个方法 |
| 3 | **Service 层不得 import 运行时** | `agent_service` 只经 `registry.get_graph(task_type)` 取图、经 `run_graph(...)` 的**返回值**（`GraphOutcome`）拿结果 | 切换时 `agent_service` 的 **15 处耦合点大部分不用改** |
| 4 | **`state` 保持纯 JSON 可序列化** | 不用 dataclass、不塞 ORM 对象（现有实现已是 `dict[str, Any]` → LONGTEXT） | LangGraph 的 `TypedDict + reducer` 是**超集** → `dict → TypedDict` 是**加法**而非改写 |
| 5 | **检查点/中断表预留三段式列** | 预留 `(thread_id, checkpoint_ns, checkpoint_id)`；`thread_id = f"{tenant_id}:{task_id}"` **只在一处生成** | 将来接 LangGraph saver 时**表结构不用改**；跨租户绕过面收到一个函数里 |
| 6 | **幂等与恢复逻辑写在业务侧** | 恢复依据 = `GraphOutcome.next_node` + `agent_step`；不依赖运行时的恢复实现 | 这套逻辑在 LangGraph 下**同样成立**，不会成为沉没成本 |

### 🔴 配套红线（唯一一处「现在顺手、将来变 bug」的地方）

**新增的图，不得把「有副作用的节点」放在 `interrupt()` 之前，或必须保证其幂等。**

原因：自研运行时的语义是「挂起后**只跑后继节点**」（人工结论存 `state["__human__"][节点名]`），
而 **LangGraph 会重放中断节点**（`interrupt()` 之前的代码会跑两遍，官方与社区文档均明确强调）。
→ 在自研下「跑一次」的代码，切到 LangGraph 后会「跑两次」。
**把副作用写在 `interrupt()` 之后、或写成幂等**，这一条在**两套运行时下都正确**。

### 结论

> **「现在不切」的成本可控，前提是 §9 的能力边界不被突破 + §10 的 6 条被遵守。**
> 建议把 §10 提升为编码纪律（并入评审文档 §8「台账更新规范」），
> 使它对**后续每一个新图**自动生效 —— 靠约定守住的边界，迟早会被人（包括未来的自己）越过。


### 10.1 落地情况（**2026-09-22 已落地为机械守卫**）

> §10 的 6 条原则**没有停在文档里** —— 它们已落成「装配期校验 + AST 守卫用例」，
> 见评审文档 **§7.3 批次 9** 与 **§8.5 图与节点编码铁律**。

| 原则 | 落地物 | 守住了什么 |
| :-: | --- | --- |
| **红线：副作用不得在 `interrupt` 之前** | `GraphDefinition.validate()` 装配期互斥校验 + AST 用例 | 中断节点一旦被声明有副作用 → **构造即抛错**（`registry` 导入时构图 ⇒ 坏声明让进程起不来） |
| **契约 2：中断点必须声明** | AST 用例比对「声明 == 代码里真实构造 `InterruptRequest` 的节点」 | 漏声明即失败 —— 否则装配期校验会被**空声明**架空 |
| **契约 3：副作用节点必须声明** | `parse` 图 4 个节点被用例钉死 | `side_effects` 成为将来启用重放 / 时间旅行时的**幂等审计清单** |
| **契约 4：图定义保持声明式** | `GraphDefinition` 只描述节点 / 边 / 中断点（无连接、无 Session） | 换运行时只需重写装配层 |
| **契约 5：节点只用 `NodeContext` 接口** | 契约 6 的同一条扫描（下划线前缀禁止） | 节点函数是切换时唯一需要改签名的面 |
| **契约 6：Service 层只用公开面** | 白名单（**12 个公开符号**）+ 禁止 import 图定义模块 | 把「切换时要改的面」锁在适配器内 |

**守卫有效性实测**：往 `field_review` 里插入一行 `record_change(...)`
（模拟 CU-16 复核工作台最可能的写法）→ 2 条用例失败并精确报出「第 9 行 + 处置办法」；
