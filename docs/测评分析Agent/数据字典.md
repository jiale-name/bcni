# 人才测评分析 Agent 数据字典

> 版本：v1.1  
> 日期：2026-09-29  
> 适用范围：P-21～P-26、API-096～API-159、TBL-29～TBL-46

本字典是后端开发启动条件之一。接口、模型、DAO、迁移和测试使用本文件中的正式名称；历史别名不得作为新代码字段名。

## 1. 命名规范

| 类别 | 正式规则 |
| --- | --- |
| 表名 | 小写下划线；测评表使用 `assessment_` 前缀；统一事件箱使用平台 `outbox_event` |
| 主键 | `id`，数据库使用 `BIGINT UNSIGNED`，接口以字符串返回 |
| 外键 | 使用 `<resource>_id`；关联报告允许为空时使用 `report_id` NULL |
| 能力维度 | 表名 `assessment_question_dimension`；编码字段 `dimension_code` |
| 题目版本 | 题目主档使用 `question_version`；发布快照必须保存题目版本 |
| 评分键 | `score_key`；维度使用 `dimension_code`，总分使用 `__total__` |
| 版本控制 | 业务版本使用 `version_no` 或领域专用版本字段；本项目评分上下文版本使用所属 Paper 的 `version_no` 并映射为 `rule_version`；并发更新使用 `row_version` |
| 时间 | 数据库 `DATETIME(3)`，服务端生成；接口使用 ISO 8601 |
| JSON | 结构化字段必须经过 Schema 校验，禁止以未定义字符串承载业务状态 |
| 审计 | 写操作记录操作者、角色、租户、组织、资源、旧状态、新状态、请求 ID、幂等键和时间 |

公共字段：除纯关联表外默认包含 `tenant_id`、按范围要求的 `org_id`、`created_at`、`created_by`、`updated_at`、`updated_by`、`row_version`、`deleted_at`；表级字段定义明确列出完整字段集合时，以表级定义为准。

TBL-37 字段契约严格只有 13 个字段：`id` BIGINT UNSIGNED PK NOT NULL；`tenant_id`、`attempt_id` BIGINT UNSIGNED NOT NULL；`client_event_id` VARCHAR(64) NOT NULL；`event_type` VARCHAR(32) NOT NULL；`occurred_at`、`received_at` DATETIME(3) NOT NULL；`duration_ms` INT UNSIGNED NULL；`metadata_summary` JSON NOT NULL；`severity` VARCHAR(16) NOT NULL；`review_status` VARCHAR(24) NOT NULL；`reviewed_by` BIGINT UNSIGNED NULL；`reviewed_at` DATETIME(3) NULL。所有字段均无数据库默认值，由应用服务显式赋值。唯一约束为 `uk_attempt_client_event(tenant_id, attempt_id, client_event_id)`；普通索引为 `idx_attempt_event_received(attempt_id, received_at, event_type)`，不创建 `(attempt_id, occurred_at, event_type)` 索引。TBL-37 不增加公共字段、`server_received_at`、`event_status` 或 `event_payload`，不创建物理 ForeignKey。

`event_type` 枚举为 `visibility_hidden`、`paste`、`idle`、`refresh`、`submit_after_deadline`、`device_change`；`severity` 枚举为 `low`、`medium`、`high`、`critical`，服务端映射为 `refresh=low`、`idle=low`、`visibility_hidden=medium`、`paste=medium`、`device_change=high`、`submit_after_deadline=critical`；`review_status` 枚举为 `unreviewed`、`reviewed`、`escalated`，API-139 创建时固定为 `unreviewed`。`received_at` 是服务端收到事件的最终字段名。

TBL-36 字段契约：严格使用 `id`、`attempt_id`、`paper_question_id`、`answer_version`、`answer`、`answered_at`、`objective_score`、`subjective_ai_score`、`final_score`、`score_source`、`review_status`、`review_comment` 共 12 个字段，不增加 `tenant_id` 或其他公共字段。`attempt_id`、`paper_question_id` 只建立逻辑关联，不创建物理 ForeignKey。唯一约束为 `uk_attempt_question_answer(attempt_id, paper_question_id)`，不创建重复普通索引。同一 Attempt 的同一题只允许一条当前答案记录；客户端首次提交 `answer_version=0`，保存成功后当前答案版本为 `1`，后续按 `N -> N+1` 更新同一记录，不保存无限历史答案。

`agent_task`、`agent_step`、`agent_interrupt` 为现有 Agent 基础表，本期复用，不新增测评专用 Agent 状态表或中断表。

## 3. 状态枚举

### 3.1 Agent 状态

持久化状态只有：

```text
queued / running / waiting_human / success / failed
```

状态流转为 `queued -> running -> waiting_human -> running -> success`，异常进入 `failed`。`resumed` 是恢复动作，不是状态；`completed` 不作为最终状态；重试是动作或次数，不是状态。

### 3.2 题目、试卷、任务和作答

| 字段 | 枚举 |
| --- | --- |
| `question_type` | `single`、`multiple`、`short_answer`、`scale` |
| `review_status` | `draft`、`pending_review`、`approved`、`rejected` |
| `enabled_status` | `enabled`、`disabled` |
| `paper_type` | `fixed`、`random` |
| `paper.status` | `draft`、`published`、`archived` |
| `task.status` | `draft`、`scheduled`、`running`、`completed`、`expired`、`archived` |
| `attempt.status` | `not_started`、`in_progress`、`submitted`、`auto_submitted`、`cancelled` |
| `task_candidate.assignment_status` | `assigned`、`started`、`submitted`、`expired`、`withdrawn` |

`completed` 仅允许作为任务业务状态，不得写入 Agent 状态。

#### 3.2.1 Attempt 契约冻结补充（人工决策）

`attempt.status` 的唯一允许集合为：

```text
not_started / in_progress / submitted / auto_submitted / cancelled
```

允许流转为 `not_started -> in_progress -> submitted`、`in_progress -> auto_submitted`、`not_started / in_progress -> cancelled`。`submitted`、`auto_submitted`、`cancelled` 为终态，禁止新增状态。

`assessment_attempt.attempt_no` 是当前任务下候选人的第 N 次 Attempt；`assessment_task_candidate.attempt_count` 是已创建 Attempt 数量，也是 `attempt_limit` 的权威计数。API-131 创建时必须锁定 Candidate 行，在同一事务中完成次数校验、序号生成、次数递增和 Attempt 创建。若已有 `in_progress` Attempt，则返回已有记录，不增加次数。

`answer_version` 初始为 `0`。答案保存必须校验客户端版本，成功后更新同一 TBL-36 当前答案记录并将 Attempt 版本加一；首次保存版本为 `1`，后续按 `N -> N+1` 更新，版本冲突使用 `40902`，不保存无限历史答案。`paper_snapshot` 在 API-131 创建时从 TBL-33 固化，API-133 只读取该快照。Attempt 在业务语义上绑定创建时任务关联的已发布 Paper 版本；本轮不新增字段或改变当前快照结构，后续评分必须使用该创建时版本。

API-138 仅接受 `confirm=true` 的正式提交，只允许 `in_progress -> submitted`。主动提交必须在同一数据库事务中完成答案冻结、Attempt 状态更新、Candidate 更新和评分任务 Outbox 事件写入。评分 Outbox 固定为 `event_type=assessment.score.requested`、`aggregate_type=assessment_attempt`，payload 严格包含 `attempt_id`、`task_id`、`tenant_id`、`answer_version`，幂等键为 `attempt_id:score:v{answer_version}`。成功响应严格只返回 `attempt_id`、`status`、`submitted_at`、`outbox_event_id`，不返回 `agent_task_id`。相同 `Idempotency-Key` 重复提交返回首次成功结果；不同 `Idempotency-Key` 提交已为 `submitted` 的 Attempt 返回 `40902`。事务成功后返回提交成功，Outbox 写入失败则整体回滚。评分 Worker 后续异步消费 Outbox，不由 API-138 等待执行完成。超时条件为服务端 `server_now >= deadline_at_snapshot`，由后台 Worker 独立触发 `in_progress -> auto_submitted`；`submit_after_deadline` 仅作为事件类型，不参与 API-138 状态转换。

API-139 中 `Idempotency-Key` 是 HTTP 请求级幂等，`client_event_id` 是客户端事件级幂等；二者不一致不视为冲突。唯一作用域为 `tenant_id + attempt_id + client_event_id`，不同 `Idempotency-Key` 携带相同事件标识时返回首次 `event_id`。`client_event_id` 为 VARCHAR(64) NOT NULL。

Candidate 联动规则固定为：API-131 成功开始时 `assignment_status=started`、`attempt_count+1`、`progress=0`、`deadline_at` 保持任务截止时间；API-134 只更新 `progress`，其他 Candidate 字段不变；API-138 主动提交时 `assignment_status=submitted`、`progress=100`；后台 Worker 自动交卷时 `assignment_status=submitted`、`progress` 按最终答案计算。四类操作均不得新增 Candidate 字段，并按冻结事务边界执行。

TBL-35 数据层最终冻结：`assessment_attempt` 仅包含表定义的 15 个字段，不增加 `org_id`、`created_at`、`created_by`、`updated_at`、`updated_by`、`row_version`、`deleted_at` 或其他字段。仅建立 `uk_attempt_task_user_no(task_id, user_id, attempt_no)` 和普通索引 `idx_attempt_task_status_saved(task_id, status, last_saved_at)`；不建立条件唯一索引或状态辅助字段。`(task_id, user_id, status)` 仅为查询优化建议。

同一 `task_id + user_id` 同时只能存在一个 `status=in_progress` 的 Attempt。后续 Attempt Service 必须锁定对应 Candidate 行，在同一事务中查询现有 `in_progress` Attempt；存在则返回已有 Attempt，不存在才创建新的 Attempt。

### 3.3 Batch 2A JSON 字段契约

`assessment_task.target_scope` 在 Batch 2A 只允许以下结构，`mode` 不得扩展为部门、岗位或动态筛选模式：

```json
{
  "mode": "explicit",
  "candidates": [
    {"talent_id": "123", "user_id": "456", "org_id": "10"}
  ]
}
```

接口输入的 `talent_id`、`user_id`、`org_id` 可以是字符串或数字，但必须能转换为 `BIGINT UNSIGNED`；接口输出统一为字符串。每个候选人必须同时包含三个字段，且同一任务内 `user_id` 不得重复。候选人和组织范围必须由服务端认证上下文及 `DataScopeFilter` 裁剪，不能由请求体扩大。

`assessment_task.notify_rules` 只允许以下结构：

```json
{
  "channels": ["in_app"],
  "notify_on": ["task_created", "reminder"]
}
```

`channels` 允许 `in_app`、`email`；`notify_on` 允许 `task_created`、`reminder`。两个数组必须存在、去重且至少包含一项。Batch 2A 只持久化通知，`assessment_notification.status` 初始值固定为 `pending`；不接入真实短信、邮件、IM 或通知调度器。

API-119～API-124 的接口分页字段固定为 `page_no`、`page_size`、`total`；不得映射为既有接口的 `page`、`per_page` 对外暴露。接口时间使用带时区的 ISO 8601 字符串；数据库时间仍使用 `DATETIME(3)`。接口 ID 统一以字符串传输。

## 4. 评分和版本规则

评分上下文版本规则：已发布 Paper 的 `version_no` 同时表示该 Paper 冻结的完整评分上下文版本。评分规则、题目版本、题目顺序、分值、客观评分规则、能力维度/维度权重快照、组卷规则或配额规则发生任何影响评分结果的变化，都必须创建新的 Paper 版本；已发布 Paper 不得原地修改。`assessment_score.rule_version` 必须等于 Attempt 创建时绑定的 Paper `version_no`，不得取当前最新 Paper 版本。

评分唯一约束为：

```text
(attempt_id, rule_version, score_key)
```

`report_id` 可以为空。评分先关联 `attempt_id`，报告生成后再关联 `report_id`，禁止使用 `report_id` 作为评分唯一键。已发布题目、试卷、评分和报告只追加版本；TBL-36 答案仅保留当前记录，不保存无限历史。

作答时长规则：`assessment_task.duration_min` 是任务配置；开始作答时写入 `assessment_attempt.duration_min_snapshot` 和 `deadline_at_snapshot`，之后只使用快照判断截止时间。

## 6. API 编号和错误码

测评接口从 `API-096` 起连续编号到 `API-159`，一个接口一个编号。通用错误码：

| code | 含义 |
| --- | --- |
| `40001` | 参数校验失败 |
| `40101` | 未认证 |
| `40301` | 无权限或组织范围不匹配 |
| `40401` | 资源不存在或不可见 |
| `40902` | 并发版本冲突或幂等键冲突 |
| `42201` | 非法状态流转 |
| `42202` | 发布前校验不通过 |
| `42301` | 已发布或资源锁定不可修改 |
| `42901` | 请求限流 |
| `50201` | 模型网关调用失败 |
| `50301` | 依赖不可用或降级 |

## 7. 页面状态词典

通用状态为 `loading / empty / error / forbidden / conflict`，仅在页面适用时要求覆盖。业务状态单独定义：P-24 使用 `reconnecting / expired / submitted / auto_submitted`；P-26 使用 `evidence_incomplete / waiting_review / published / superseded`。不适用状态不强行增加。

## 8. 版本和变更要求

本字典字段或枚举发生变更时，必须同步更新需求、架构、数据库、接口、开发实施和约束文档，并增加迁移、兼容性说明、契约测试和验收记录。六项启动条件全部对齐后，才允许开始后端业务实现。
