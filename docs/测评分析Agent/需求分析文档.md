# 人才测评分析 Agent 需求分析与设计规格

> 版本：v0.1（待评审）  
> 日期：2026-09-28  
> 适用范围：本期人才测评分析 Agent，承接现有 AI 数字化人才平台 F-4 需求与 F-A0 Agent 基座。

## 1. 目标

本期建设一条可审计的人才测评闭环：HR 创建题目和测评任务，候选人在线作答，系统记录作答过程中的异常行为，客观题由确定性规则评分，主观题由模型生成辅助分析，系统输出带题目/得分证据的能力报告，经人工复核后才发布到人才画像。

本期的核心交付不是“让模型替 HR 做决定”，而是让测评组织、作答、评分、分析和证据追溯形成可执行的业务链路。所有影响个人权益的能力结论和报告发布动作均保留人工确认点。

## 2. 本期范围

### 2.1 包含范围

| 子域 | 本期交付 | 对应原需求 |
| --- | --- | --- |
| 题库 | 题目录入、编辑、版本、能力维度、知识点、难度、题型、答案、解析、审核状态机、题目启停、审核留痕 | F-4.1、F-4.9 |
| 组卷 | 固定卷、随机卷、按岗位/层级/专业方向/难度/知识点筛选、题目配额校验、预览、发布 | F-4.1 |
| 在线作答 | 测评任务、开始/截止时间、时长、次数限制、断点保存、自动交卷、提交确认、作答结果 | F-4.2、F-4.3 |
| 作答监控 | 切屏、粘贴、长时间无操作、重复刷新、设备/浏览器指纹摘要、异常阈值、异常标记和复核入口 | F-4.3 |
| 能力报告 | 确定性评分、主观题 AI 辅助分析、5~8 维能力雷达、优势/短板、提升建议、题目/得分证据、人工复核、PDF 导出 | F-4.4、F-4.5、F-4.6 |

### 2.2 明确不包含

以下功能不进入本期开发范围，但数据模型和页面入口可预留扩展点：

- 动态能力评级自动更新及其与培训数据的长期融合（F-4.7）。本期只生成一次测评报告并支持人工确认后写入画像快照。
- 培训计划、课程推荐、复测提升闭环（F-7）。
- 岗位-人才精准匹配（F-6）。
- NL2SQL 测评大盘、PgSQL/CDC/TimescaleDB 分析副本（F-5）。本期看板只使用测评域业务库的聚合查询。
- 移动端原生应用、第三方邮件/短信供应商的深度接入。本期保留通知适配接口，默认使用站内通知或开发环境模拟发送。
- 远程摄像头监考、活体检测、屏幕录像。作答监控只记录浏览器可获得的事件，不宣称具备考试防作弊的全部能力。

## 4. 业务流程

### 4.1 题目生命周期

```text
草稿 → AI 生成/人工录入 → 待专家审核 → 已审核 → 已启用 → 已停用
                         └──────────────→ 退回修改 → 草稿
```

规则：

1. 只有“已审核”且“已启用”的题目允许进入新试卷。
2. 已被已发布试卷引用的题目不能原地改写答案、分值、能力维度或正确选项；编辑必须创建新版本。
3. 停用题目不影响历史作答、历史评分和历史报告，只禁止新组卷引用。
4. AI 生成题目必须保存生成模型、Prompt 版本、生成时间和审核人；人工录入题目将来源标记为 `manual`。
5. 主观题不存“唯一正确答案”作为评分事实，保存评分要点、参考答案和评分量表，供人工和 AI 辅助使用。

### 4.2 组卷与发布流程

```text
新建试卷 → 选择固定/随机 → 配置题目规则 → 预览与校验 → 保存草稿
                                                     ↓
                                           发布（冻结题目版本）
                                                     ↓
                                      创建测评任务并分配被测人员
```

固定卷保存明确的题目版本列表和顺序。随机卷保存抽题规则、随机种子、实际抽取结果和题目版本列表；发布后不得重新抽题。发布校验至少包括：题目数量、总分、各题型配额、能力维度覆盖、所有题目已审核启用、选项与答案完整、时长和截止时间合法。

Paper 发布版本契约：已发布 Paper 的 `version_no` 表示本次测评冻结的完整评分上下文版本，同时冻结试卷内容、题目及题目版本、题目顺序、分值、客观评分规则、能力维度及维度权重快照、组卷规则和配额规则。任何会影响评分结果的内容变更（包括只修改评分规则而不修改题目内容）都必须创建新的 Paper 版本，不得原地修改已发布 Paper。

### 4.3 在线作答流程

```text
待开始 → 作答中 → 作答中（断点保存/暂停动作） → 作答中 → 已提交
                                                    └──后台 Worker 超时自动交卷──┘
```

1. 候选人只能在任务有效期内开始，开始后生成一次作答实例和服务端开始时间。
2. 每次保存只接受当前作答实例和递增版本号；旧版本请求返回并发冲突，不能覆盖更新后的当前答案。
3. 客观题答案在提交后由服务端评分；浏览器不得获得可用于作弊的标准答案或评分逻辑细节。
4. 主观题答案原文只在授权的评分/复核界面展示；候选人只能看到题目要求和自己的作答，不看到他人答案。
5. 交卷后不可再次修改。网络中断时允许在截止时间前恢复未提交草稿，不能延长服务端截止时间。

#### 4.3.1 Attempt 契约冻结补充（人工决策）

本节冻结 API-131～API-139 的 Attempt 核心行为；未在本节明确的请求字段、响应字段和错误语义仍不得由实现自行补充。

1. Attempt 状态仅允许 `not_started`、`in_progress`、`submitted`、`auto_submitted`、`cancelled`。允许流转为：
   - `not_started -> in_progress -> submitted`；
   - `in_progress -> auto_submitted`；
   - `not_started / in_progress -> cancelled`。
   `submitted`、`auto_submitted`、`cancelled` 为终态，禁止新增状态。
2. API-131 首次开始作答时创建 Attempt。已有状态为 `in_progress` 且未提交的 Attempt 时，直接返回已有 Attempt，不创建新记录且不增加 `attempt_count`。已有终态 Attempt 时，依据 `attempt_limit` 判断是否允许创建下一次。
3. API-131 必须使用服务端时间，并在同一事务中生成 `paper_snapshot`、`duration_min_snapshot`、`deadline_at_snapshot`、`attempt_no`，同时完成 Candidate 的次数更新。创建时锁定 Candidate 行，校验 `attempt_count < attempt_limit`，生成本次 `attempt_no`，再将 `attempt_count` 加一并创建 Attempt。
4. `assessment_attempt.attempt_no` 表示当前任务下该候选人的第 N 次 Attempt；`assessment_task_candidate.attempt_count` 表示已创建 Attempt 数量，并作为 `attempt_limit` 校验依据。
5. `assessment_attempt.answer_version` 初始值为 `0`。客户端首次提交 `answer_version=0`，服务端校验成功后将当前 `assessment_answer` 写入/更新为 `answer_version=1`，并将 Attempt 版本更新为 `1`；后续保存按 `N -> N+1` 更新同一答案记录。版本冲突返回 `40902`，不得覆盖其他并发版本，不保存无限历史答案。
6. `paper_snapshot` 来源于 TBL-33 `assessment_paper_question`，在 API-131 创建 Attempt 时生成，至少固化题目 ID、题目版本、题型、题干、选项、选项顺序、分值、题目顺序以及文档已定义的其他题目快照字段。API-133 只读取 Attempt 快照，已创建 Attempt 不实时读取题库内容。Attempt 在业务语义上必须绑定创建时任务所关联的已发布 Paper 版本；本轮不新增 Attempt 字段、不改变当前 `paper_snapshot` 结构，后续实现必须保证评分使用该创建时版本而不是当前最新 Paper。
7. API-138 仅在 `confirm=true` 时允许正式提交，只允许 `in_progress -> submitted`。提交事务必须锁定 Attempt、校验 `status=in_progress`、执行提交前检查、冻结答案、写入提交时间、更新 Candidate，并写入评分任务 Outbox 事件；答案冻结、Attempt 状态更新、Candidate 更新和 Outbox 写入必须处于同一数据库事务。评分 Outbox 固定为 `event_type=assessment.score.requested`、`aggregate_type=assessment_attempt`，payload 严格为 `attempt_id`、`task_id`、`tenant_id`、`answer_version`，幂等键为 `attempt_id:score:v{answer_version}`。成功响应严格返回 `attempt_id`、`status`、`submitted_at`、`outbox_event_id`，不返回 `agent_task_id`。事务成功后返回提交成功，评分 Worker 后续异步消费 Outbox；Outbox 写入失败时整个事务回滚。相同 `Idempotency-Key` 重复提交返回首次成功结果；不同 `Idempotency-Key` 提交已为 `submitted` 的 Attempt 返回 `40902`。与超时 Worker 并发时由数据库状态锁保证仅一个请求完成提交。
8. `auto_submitted` 只能由后台 Worker 根据 `server_now >= deadline_at_snapshot` 触发，且仅允许 `in_progress -> auto_submitted`。自动交卷与主动提交使用相同的答案冻结、提交时间、评分任务创建和 Candidate 更新原则。
9. API-139 的 `Idempotency-Key` 是 HTTP 请求级幂等，`client_event_id` 是客户端事件级幂等；二者不一致不视为冲突。唯一作用域为 `tenant_id + attempt_id + client_event_id`。不同 `Idempotency-Key` 携带相同事件标识时返回首次创建的 `event_id`，不创建新事件且不产生重复事件副作用。`client_event_id` 为 VARCHAR(64) NOT NULL。

Candidate 联动规则固定如下，且不得新增 Candidate 字段：

| 操作 | `assignment_status` | `attempt_count` | `progress` | `deadline_at` | 事务边界 |
| --- | --- | --- | --- | --- | --- |
| API-131 成功开始 | `started` | 加 1 | `0` | 保持任务截止时间 | 与 Attempt 创建同一事务 |
| API-134 保存答案 | 不变 | 不变 | 更新为当前作答进度 | 不变 | 与答案保存同一事务 |
| API-138 主动提交 | `submitted` | 不变 | `100` | 不变 | 与 Attempt 提交同一事务 |
| 后台 Worker 自动交卷 | `submitted` | 不变 | 按最终答案计算 | 不变 | 与 Attempt 自动交卷同一事务 |

“暂停作答”仅表示前端/业务动作，不是 Attempt 状态；Attempt 状态仍只能使用本节冻结的五个值。

#### 4.3.2 TBL-35 数据层最终冻结

`assessment_attempt` 严格使用数据库设计文档定义的 15 个字段：`id`、`tenant_id`、`task_id`、`talent_id`、`user_id`、`paper_snapshot`、`attempt_no`、`answer_version`、`started_at`、`duration_min_snapshot`、`deadline_at_snapshot`、`last_saved_at`、`submitted_at`、`status`、`client_device_hash`。TBL-35 不增加 `org_id`、`created_at`、`created_by`、`updated_at`、`updated_by`、`row_version`、`deleted_at` 或其他公共/业务字段；本表级定义优先于业务表公共字段默认规则。

TBL-35 仅建立唯一约束 `uk_attempt_task_user_no(task_id, user_id, attempt_no)`，以及普通索引 `idx_attempt_task_status_saved(task_id, status, last_saved_at)`。不建立条件唯一索引，不新增 `is_active`、`active_flag` 或其他状态辅助字段。架构层的 `(task_id, user_id, status)` 仅作为查询优化建议，不创建为本表物理索引。

同一 `task_id + user_id` 同时只能存在一个 `status=in_progress` 的 Attempt。该规则由后续 Attempt Service 在同一事务中锁定对应 `assessment_task_candidate` 行、查询现有 `in_progress` Attempt 并在不存在时创建新 Attempt 保证；存在时返回已有 Attempt，不由数据库条件唯一约束保证。

### 4.4 分析 Agent 流程

```text
提交作答
   ↓
校验任务与作答完整性
   ↓
客观题确定性评分 ───────┐
                        ├→ 维度聚合与一致性校验
主观题证据切分 → AI 初评 ─┘
                               ↓
                    生成带证据引用的报告草稿
                               ↓
                    命中抽检/临界分/高影响结论？
                         ├─ 是 → 人工复核待办
                         └─ 否 → 仍进入发布前确认
                               ↓
                        HR 确认并发布报告
                               ↓
                        写入人才画像测评快照
```

分析 Agent 必须注册为现有 `agent_task.task_type = "score"` 的图定义，状态统一为 `queued → running → waiting_human → running → success`，异常进入 `failed`。`resumed` 是恢复动作，不是状态；`completed` 不作为最终状态。每个节点写入 `agent_step`，报告草稿、评分明细、证据引用和模型调用记录可回放。模型只负责主观题辅助分析和文字组织，不得修改客观题分数，不得无证据生成能力结论。

## 5. 评分与报告规则

### 5.1 客观题

客观题评分是唯一事实来源，使用服务端确定性代码计算：

- 单选/判断：答案完全一致得该题分，否则 0 分。
- 多选：默认全对得分、错选 0 分、漏选 0 分；规则作为试卷级配置保存，不由模型决定。
- 填空：采用标准答案集合、大小写/空白归一化和可配置同义词；命中规则由服务端执行并保留判定原因。
- 量表题：按选项分值直接映射，不调用模型。

每道题保存 `raw_score`、`max_score`、`scoring_rule_version` 和 `evidence_ref`。本项目中评分规则版本统一由该题所属 Attempt 对应的 Paper `version_no` 表示，即 `assessment_score.rule_version = assessment_paper.version_no`；重算必须使用原 Paper 版本规则，不能因为规则升级改变历史已发布报告。

评分快照允许在报告生成前存在，`report_id` 可以为空；评分记录使用 `(attempt_id, rule_version, score_key)` 唯一约束，其中 `rule_version` 必须等于该 Attempt 创建时绑定的 Paper `version_no`。报告生成后再把评分快照关联到 `report_id`，不能以报告 ID 作为评分唯一键。

### 5.2 主观题

主观题分析分两层：

1. 服务端先保存原答案、题目要求、评分维度和评分要点。
2. AI 输出建议分、建议等级、优点、风险点、引用的答案片段和置信度；建议结果标记为 `ai_draft`，不得直接成为最终分。
3. HR 在复核界面确认或修改分数、理由和证据；最终结果标记为 `human_confirmed`。
4. 模型无有效证据时必须输出“证据不足”，不得补写候选人未表达的经历或能力。

主观题出网遵循现有 F-3.9 脱敏链路：模型上下文使用候选人占位符，返回结果在服务端本地回填；AI 调用日志保存模型、Prompt 版本、耗时、token、脱敏状态和失败原因。

### 5.3 能力维度聚合

本期支持 5~8 个能力维度。每个题目至少绑定一个能力维度和权重；维度分数按题目最终得分加权归一化：

```text
dimension_score = sum(question_final_score × question_dimension_weight)
                   / sum(question_max_score × question_dimension_weight)
                   × 100
```

报告必须同时展示：维度分数、等级区间、组成题目数、客观/主观占比、人工确认覆盖情况。模型可以把这些确定性数据组织成文字，但不能改写维度分数。

### 5.4 报告内容与证据引用

报告草稿至少包含：

- 测评基本信息：测评名称、试卷版本、作答时间、完成度、异常事件摘要。
- 总分与维度雷达图：总分、各维度分数、评分口径和版本。
- 能力结构分析：优势、短板、风险提示。
- 提升建议：每条建议必须关联一个能力维度和至少一条题目/得分证据。
- 证据清单：题目编号、题干摘要、作答摘要、最终得分、来源类型、查看权限。
- 复核信息：AI 初评覆盖率、人工确认人、确认时间、报告版本和发布状态。

证据引用使用稳定的 `evidence_id`，不得只保存模型生成的自然语言编号。报告中的每条结论必须至少绑定一条证据；无法绑定时结论状态为 `unsupported`，报告不得发布。证据原文按角色裁剪，MGR/EMP 只能看到允许范围内的题目和本人答案。

### 5.5 发布控制

报告状态：

```text
draft → waiting_review → approved → published
                 └────────→ returned → draft
published → superseded（重新测评或人工修订后）
```

发布前必须满足：客观题评分完成、主观题抽检规则满足、所有高影响结论有人确认、证据引用完整、异常事件已处置或已明确标记；报告引用的评分、题目和证据上下文必须来自该 Attempt 创建时绑定的 Paper 版本。报告自身的 `version_no` 是报告版本，可在同一 Attempt 下独立递增。发布动作写审计日志，并生成可回看的报告快照。

## 6. 作答监控规则

监控只记录事件，不直接自动判定作弊或取消成绩。事件类型和默认建议阈值如下，阈值需要在系统配置中可调：

| 事件 | 记录内容 | 默认阈值 | 处置 |
| --- | --- | ---: | --- |
| `visibility_hidden` | 切出页面开始/结束、累计时长 | 单次 > 10 秒 | 累计次数和时长进入异常摘要 |
| `paste` | 题目区、时间、内容长度摘要 | 单次即记录 | 不保存剪贴板原文，避免收集无关个人信息 |
| `idle` | 开始/结束、持续时长 | > 5 分钟 | 提醒候选人；不自动扣分 |
| `refresh` | 页面刷新、客户端版本 | 10 分钟内 ≥ 5 次 | 标记高频刷新 |
| `submit_after_deadline` | 客户端提交时间、服务端接收时间 | 超过截止时间 | 仅作为事件类型记录，不参与 API-138 状态转换；API-138 只能执行 `in_progress -> submitted` |
| `device_change` | 设备指纹摘要变化 | 任务内出现新设备 | 进入异常复核摘要 |

安全边界：不采集剪贴板原文，不默认采集摄像头/麦克风，不把浏览器事件直接输入模型生成“作弊结论”。最终是否异常由 HR 按证据确认，异常事件只影响报告风险提示和复核队列，不静默修改分数。

TBL-37 事件幂等约束：`client_event_id` 为 VARCHAR(64) NOT NULL，用于客户端事件幂等；唯一约束为 `UNIQUE (tenant_id, attempt_id, client_event_id)`，约束名为 `uk_attempt_client_event`。重复事件不创建新事件，返回首次创建的 `event_id`，且不产生重复事件副作用。

TBL-37 字段契约严格只有以下 13 个字段：`id` BIGINT UNSIGNED PK NOT NULL、`tenant_id` BIGINT UNSIGNED NOT NULL、`attempt_id` BIGINT UNSIGNED NOT NULL、`client_event_id` VARCHAR(64) NOT NULL、`event_type` VARCHAR(32) NOT NULL、`occurred_at` DATETIME(3) NOT NULL、`received_at` DATETIME(3) NOT NULL、`duration_ms` INT UNSIGNED NULL、`metadata_summary` JSON NOT NULL、`severity` VARCHAR(16) NOT NULL、`review_status` VARCHAR(24) NOT NULL、`reviewed_by` BIGINT UNSIGNED NULL、`reviewed_at` DATETIME(3) NULL。所有字段均无数据库默认值，由应用服务显式赋值。TBL-37 不包含任何额外公共字段、`server_received_at`、`event_status` 或 `event_payload`，也不创建物理 ForeignKey。

TBL-37 仅建立普通索引 `idx_attempt_event_received(attempt_id, received_at, event_type)`，不建立 `(attempt_id, occurred_at, event_type)` 索引。`event_type` 枚举为 `visibility_hidden`、`paste`、`idle`、`refresh`、`submit_after_deadline`、`device_change`；`severity` 枚举为 `low`、`medium`、`high`、`critical`，由服务端按事件类型分别映射为 `refresh=low`、`idle=low`、`visibility_hidden=medium`、`paste=medium`、`device_change=high`、`submit_after_deadline=critical`；`review_status` 枚举为 `unreviewed`、`reviewed`、`escalated`，API-139 创建时固定为 `unreviewed`。API-139 成功响应严格为 `{"event_id": "123456"}`。

## 8. Agent 图设计

`score` 图建议拆为以下节点，全部纳入现有注册表和步骤回放：

```text
validate_attempt
  → score_objective
  → aggregate_dimensions
  → prepare_subjective_evidence
  → ai_review_subjective
  → build_report_draft
  → review_gate (interrupt)
  → publish_report
  → sync_talent_profile
```

节点约束：

- `score_objective` 只能调用确定性评分器；禁止调用模型。
- `ai_review_subjective` 只能产生建议字段，不能写入最终分。
- `build_report_draft` 必须检查每条结论是否有 `evidence_id`。
 - `review_gate` 复用现有 `agent_interrupt` 产生人工待办，处理后从断点恢复。
 - `publish_report` 在本地事务中写发布快照和 `outbox_event`；`sync_talent_profile` 在事务外消费并可重试，跨库画像同步失败时保留补偿事件，不报告虚假成功。

## 9. 接口与页面基线

### 9.1 建议接口域

接口编号继续沿用现有 API-01~API-095，新增测评接口从 API-096 开始，连续扩展至 API-159；一个接口对应一个 API 编号，不合并接口、不为压缩编号强行收敛到 API-131：

| 接口组 | 建议接口 | 用途 |
| --- | --- | --- |
| 题库与维度 | API-096~API-108 | 维度、题目列表、详情、模板、导出、创建、版本、审核、启停 |
| 试卷 | API-109~API-118 | 试卷草稿、题目池、加入/移除/排序、校验、发布 |

| 监控 | API-140~API-149 | 结果、导出、事件、核查、待办、分布、规则配置 |
| 报告 | API-150~API-159 | 报告、评分、版本、证据、复核、导出、发布、Agent 回放 |

统一遵循现有 API 约定：`code == 0` 才是成功，所有 ID 以字符串传输，租户/组织/本人范围不接受前端伪造，写接口支持幂等键，状态冲突使用 `40902`，非法状态流转使用 `42201`，无权限使用 `40301`。

## 10. 验收标准

### 10.1 题库与组卷

- 未审核或已停用题目无法进入新试卷，接口返回可识别业务错误。
- 已发布试卷保留题目版本和随机种子，重新打开试卷得到相同题目顺序。
- 固定卷和随机卷均可通过预览看到题目、分值、维度覆盖和总分。
- 题目编辑产生版本，不改变历史作答使用的题干、选项、答案和评分规则；已发布 Paper 的评分规则发生变化时，即使题目内容不变，也必须创建新的 Paper 版本。

### 10.2 在线作答与监控

- 服务端时间决定开始、截止、自动交卷和超时，客户端时间不能延长作答。
- 断点保存使用版本号，旧请求不能覆盖新答案。
- 监控事件可按尝试实例回放；不保存剪贴板原文，不自动生成“作弊定论”。
- 候选人只能访问本人任务和本人报告，跨租户/跨人访问返回统一权限错误。

### 10.3 分析 Agent 与报告

- 客观题分数可由同一份快照重复计算得到相同结果，评分过程不调用模型。
- 主观题 AI 输出明确标记为辅助结果；未人工确认不得进入已发布报告。
- 每条优势、短板和建议至少有一个稳定证据引用；缺证据的报告不能发布。
- 报告能下钻到题目、作答摘要、得分和评分来源；历史版本可查看但不可覆盖。
- Agent 失败可从最后成功节点重试；人工驳回有意见，发布/回滚/导出均写审计日志。

### 10.4 非功能与安全

- 所有接口经过现有 RBAC、租户和组织范围校验。
- 题目答案、主观作答和报告敏感内容按角色裁剪，模型调用经过脱敏链路。
- Agent 任务、步骤、AI 调用、业务审计四类记录可通过任务 ID 串联。
- 本期不宣称摄像头监考或自动作弊判定；产品文案必须保持“异常事件提示/人工复核”。

## 11. 交付拆分建议

后续开发按四批执行，每批都必须有独立可运行代码、测试、迁移和验收记录：

1. 第一批：P-21/P-22，TBL-29~TBL-33，题库、能力维度、组卷和试卷发布。
2. 第二批：P-23/P-24，TBL-34~TBL-36、TBL-43、TBL-45，任务分配、通知、在线作答和服务端时间。
3. 第三批：P-25/P-26，拆成 3A 监控+异常+人工复核、3B 评分+证据、3C 报告+发布+画像补偿。
4. 第四批：P-21~P-26 全链路联调、权限、审计、错误态、性能、安全、迁移回滚和验收。

第三批内部 3A/3B/3C 仍属于同一批次，但每个检查点必须独立测试；3B 不依赖 3C 才能运行。

## 12. 待评审决策

以下事项已在本规格中给出推荐默认值，实施前需要评审确认：

1. 多选题默认采用“全对得分、错选 0 分、漏选 0 分”，是否接受。
2. 量表题和等级规则是否由管理员配置，还是由系统固定一套模板。
3. 主观题 AI 初评是否允许给出建议分；推荐允许，但最终分必须人工确认。
4. 候选人报告是否在 HR 发布后可见；推荐是，未发布报告对候选人不可见。
5. 作答监控默认事件阈值是否采用第 6 节数值。
6. 本期是否使用站内通知模拟器作为通知实现，第三方短信/邮件只保留适配接口。

## 13. 与现有项目的对齐结论

- 复用 `agent_task`、`agent_step`、`agent_interrupt`，不新增第二套 Agent 状态机。

- 复用人才主档和画像标签；本期新增的是“测评能力快照”，不直接覆盖原有履历或技能事实。
