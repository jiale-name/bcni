## 1. 目标

本期建设一条**可审计、可解释、可回溯**的人才画像闭环：以人才主档与受控标签为底座，消费履历事实与测评能力快照，按**确定性规则**聚合出分层的人才画像，由模型在脱敏前提下组织画像文字描述，经**人工复核**后发布为**版本化画像快照**，并支持画像查看、版本对比、差异归因与导出。

本期的核心交付不是"让模型给人打分"，而是让**多源事实 → 画像维度 → 可举证结论**形成一条可追溯的业务链路。所有影响个人权益的能力结论，以及画像的发布动作，均保留人工确认点。

### 1.1 与既有资产的边界（最重要的一节）

本项目**已经存在两层"画像"**，本智能体必须与之划清边界，否则会出现"同一份画像三个来源"的口径崩坏：

| 既有资产 | 现有含义 | 本智能体的关系 |
| --- | --- | --- |
| **F-3.4 向量画像**（`talent_base.profile_vec_id` + `COL-01~03`） | 面向**检索**的技能 / 经验 / 素质**向量**，服务语义检索与查重 | **只读复用**。本智能体不生成、不改写向量；画像快照发布后按既有 `_reindex_talent` 约定触发重索引，不新增向量集合 |
| **F-3.4.1 受控标签**（`talent_tag_dict` / `talent_tag_rel`） | 画像**标签**，只能取自受控词表启用项 | **只读复用**。画像可引用标签作为证据来源，但不得造标签、不得直接写 `talent_tag_rel` |
| **人才测评分析 Agent**（`assessment_score` / `assessment_report`） | 测评产出的**能力快照**（维度分 / 总分），已 `published` | **事件消费**。测评报告发布后经 `outbox_event` 触发画像重算；画像**不重新评分** |
| **本智能体（新增）** | 面向**人**的统一、分层、可解释画像**快照**（维度分 + 等级 + 描述 + 证据 + 版本） | 只**派生**、不覆盖任何事实来源字段 |

> 🔴 **铁律**：画像快照是**派生数据**，永远不能作为 `talent_base` / `talent_skill` / `assessment_score` 的事实来源，也不得反向覆盖它们。

### 1.2 本期核心命题

1. **口径唯一**：同一 `talent_id` + 同一配置版本，画像可**重复计算得到相同结果**（确定性聚合）。
2. **可举证**：画像的每条维度结论与每段描述都必须绑定稳定的 `evidence_id`，可反向定位到档案字段 / 标签 / 测评评分快照。
3. **可回溯**：画像只追加版本；历史版本可按权限查看，不得原地覆盖。
4. **人在环**：低置信度、来源冲突、高影响结论必须进入人工复核，未确认不得发布。

### 2.2 明确不包含

以下不进入本期开发范围，但数据模型与接口预留扩展点：

- **岗位-人才精准匹配（F-6）**：本期不做匹配公式、岗位结构化解析与匹配解释；画像只提供维度分作为未来匹配的输入。
- **培训计划与成长闭环（F-7）**：不生成课程推荐与学习计划。
- **测评评分本身（F-4）**：不重新评分、不修改 `assessment_score` / `assessment_report`，只消费已发布快照。
- **NL2SQL 画像大盘 / PgSQL 分析副本（F-5）**：本期看板只使用画像域业务库的聚合查询。
- **动态能力评级自动更新**：本期只生成版本化快照并支持人工确认后发布，不做无人工的自动评级生效。
- **画像向量化与检索**：不新增 Milvus 集合，不改变 COL-01~03 语义。
- **移动端原生应用 / 第三方通知深度接入**：保留通知适配接口，默认站内通知或开发环境模拟。

## 4. 业务流程

### 4.1 画像生命周期

```text
                    ┌──────────── 触发（手动 / 事件 / 批量 / 定时）────────────┐
                    ▼                                                          │
              （来源装配）                                                     │
                    │                                                          │
                    ▼                                                          │
   draft ──► computing ──► evidence_incomplete ──（补证据）──► computing       │
                    │                                                          │
                    │ 确定性聚合 + 描述生成                                     │
                    ▼                                                          │
            waiting_review ──（退回）──► returned ────────────────────────────┘
                    │
                    │（人工确认）
                    ▼
                approved ──► published ──► superseded（新版本替代）
```

规则：

1. 画像快照状态只允许：`draft`、`computing`、`evidence_incomplete`、`waiting_review`、`returned`、`approved`、`published`、`superseded`。**禁止实现自行新增状态**。
2. `published` 为不可覆盖的版本快照；同一 `talent_id` 下新版本发布后，旧版本标记为 `superseded` 但仍可按权限查看。
3. 缺证据或存在来源冲突时，停留在 `evidence_incomplete`，发布按钮禁用。
4. 高影响结论（总分等级阈值跨越、维度等级下降、与上一版本差异超过阈值）必须人工确认。
5. 发布动作写审计日志，并生成可回看的画像快照。

### 4.2 触发与幂等

| 触发方式 | 说明 | 幂等键建议 |
| --- | --- | --- |
| 手动重算 | ADM/HR 对单个或批量人才发起 | `talent_id:profile:manual:{client_request_id}` |
| 事件触发 | 消费 `outbox_event`：档案变更 / 测评报告发布 | `talent_id:profile:v{config_version}:{source_version}` |
| 定时批量 | 按配置周期对"来源已变更且未重算"的人才重算 | 同上，按批次键去重 |

- 事件触发**必须先去重再执行**：同一来源版本重复投递不得产生第二个画像版本。
- 重算入口在**重试 / 重入前必须先作废旧幂等键**（承接批次 22/24 的幂等回放纪律）。

### 4.3 画像合成 Agent 流程

```text
装载来源（档案事实 + 标签 + 测评能力快照 + 变更留痕）
   ↓
校验来源完整性与配置版本
   ↓
确定性维度聚合（规则引擎） ────────┐
                                   ├→ 一致性校验（来源冲突 / 缺失降级）
主观维度？ → 证据切分 → AI 辅助描述 ┘
                                   ↓
                      生成带 evidence_id 的画像草稿
                                   ↓
                      命中复核规则（低置信度 / 冲突 / 高影响）？
                          ├─ 是 → 人工复核待办（agent_interrupt）
                          └─ 否 → 仍进入发布前确认
                                   ↓
                        HR/ADM 确认并发布画像快照
                                   ↓
                 触发向量重索引（既有约定）+ 写审计 + 落 outbox 事件
```

Agent 必须注册为现有 `agent_task.task_type = "profile"` 的图定义，状态统一为 `queued → running → waiting_human → running → success`，异常进入 `failed`。`resumed` 是恢复动作，不是状态；`completed` 不作为 Agent 状态。每个节点写入 `agent_step`，画像草稿、维度分、证据引用和模型调用记录可回放。

## 5. 画像模型与聚合规则

### 5.1 画像维度体系

本期采用**可配置维度**，默认提供一套模板（≥5 且 ≤8 个维度），维度编码示例：

| `dimension_code` | 名称 | 主要来源 | 是否需模型 |
| --- | --- | --- | --- |
| `education_background` | 教育背景 | 学历 / 院校 / 专业 | 否（确定性） |
| `work_experience` | 工作经历 | 工作年限 / 履历连续性 | 否（确定性） |
| `professional_skill` | 专业技能 | 技能明细 + 技能标签 | 否（确定性） |
| `project_achievement` | 项目成果 | 项目经历数量 / 角色层次 | 否（确定性） |
| `certification` | 资质证书 | 证书明细 | 否（确定性） |
| `assessment_capability` | 测评能力 | 测评能力快照（维度分） | 否（消费快照） |
| `potential` | 发展潜力 | 由上述维度派生 + 模型描述 | 是（仅描述） |

规则：

1. 维度权重与等级规则由配置表承载，**发布后冻结快照**；任何影响画像结果的变化都必须创建新的**配置版本**，不得原地修改已发布配置。
2. 每个维度的分数必须能归因到至少一个来源（档案字段 / 标签 / 测评快照）。
3. 标签作为画像来源时，**只能取自 `talent_tag_dict.status=1` 的启用项**（承接 F-3.4.1 硬约束）。

### 5.2 确定性聚合规则

画像维度分是**唯一事实来源**，由服务端确定性代码计算：

```text
dimension_score = Σ( source_item_score × source_weight )
                  / Σ( source_item_max   × source_weight ) × 100
```

- 来源权重、归一化口径、等级区间全部来自**配置版本快照**，不由模型决定。
- 来源缺失时**显式降级**：该来源不参与分母并标记 `source_missing`，**不得用 0 分顶替**（否则会把"没数据"算成"能力差"）。
- 每个维度保存 `score`、`level`、`weight`、`source_mix`、`score_source`、`config_version`。
- **模型不得修改任何维度分**，只能把确定性数据组织成文字。

### 5.3 画像描述生成（模型层）

1. 描述分两层：确定性数据（维度分 / 等级 / 来源覆盖）由服务端生成；文字描述由模型组织。
2. 模型输出必须：引用 `evidence_id`、标注 `ai_draft`、给出置信度；**不得无证据生成能力结论**。
3. 模型无有效证据时必须输出"证据不足"，**不得补写候选人未表达的经历或能力**。
4. 出网遵循现有脱敏链路：上下文使用占位符（`{{CANDIDATE}}` / `{{PHONE}}` / `{{EMAIL}}` / `{{ID}}`），送出前二次 NER 校验，返回后本地回填；AI 调用日志保存模型、Prompt 版本、耗时、token、`deployment`、脱敏状态与失败原因。
5. 人工确认后，描述标记为 `human_confirmed`。

### 5.4 证据模型

每条维度结论与每段描述至少绑定一个稳定 `evidence_id`，证据包含：

```json
{
  "evidence_id": "PE-20261012-001-03",
  "snapshot_id": "S-20261012-001",
  "source_type": "assessment_snapshot",
  "source_ref": {"table": "assessment_score", "id": "123456", "version": "7"},
  "dimension_code": "assessment_capability",
  "quote": "测评维度 team_collaboration 得分 78，等级 B。",
  "score_snapshot": {"score": 78, "level": "B", "max": 100},
  "status": "complete"
}
```

- `source_type` 枚举：`talent_fact`、`tag`、`assessment_snapshot`、`changed_log`。
- 证据必须携带**来源版本**（档案 `version_no` / 测评 `published` 版本 / 配置版本），版本不一致的证据不得进入已发布画像。
- 无法绑定证据的结论状态为 `unsupported`，**画像不得发布**。

### 5.5 发布控制

发布前必须满足：

1. 所有启用维度均已计算完成。
2. 所有高影响结论有人工确认记录。
3. 所有结论与描述至少有一个 `evidence_id`。
4. 证据来源版本与本次配置版本一致。
5. `unsupported` 结论为零。

发布动作写审计日志，并生成不可覆盖的画像快照；随后按既有约定触发向量重索引，并落 `outbox_event`（失败进入补偿队列，**不回滚已发布画像**）。

## 7. Agent 图设计

`profile` 图建议拆为以下节点，全部纳入现有注册表和步骤回放：

```text
load_sources
  → validate_inputs
  → aggregate_dimensions        # 确定性，禁止调模型
  → check_consistency           # 来源冲突 / 缺失降级
  → prepare_description_evidence
  → ai_describe                 # 只产文字与建议，不改数值
  → build_profile_draft         # 每条结论必须带 evidence_id
  → review_gate (interrupt)
  → publish_profile
  → trigger_reindex             # 复用既有向量重索引约定
  → emit_outbox                 # 画像已发布事件
```

节点约束：

| 节点 | 输入 | 输出 | 约束 |
| --- | --- | --- | --- |
| `load_sources` | `talent_id`、来源开关 | 来源装配快照 | 只读，不写任何事实表 |
| `validate_inputs` | 来源快照、配置版本 | 可计算性结论 | 配置版本缺失则阻断，不得用默认配置静默计算 |
| `aggregate_dimensions` | 档案事实 / 标签 / 测评快照 | 维度分与总分基线 | 只调用规则引擎，**不调用模型**，结果可重复 |
| `check_consistency` | 维度分、来源覆盖 | 冲突与降级清单 | 缺失来源显式标记，不用 0 分顶替 |
| `prepare_description_evidence` | 维度分、来源片段 | 脱敏描述素材 | 不发送无关个人信息与原文 PII |
| `ai_describe` | 脱敏素材、Prompt 版本 | 描述草稿、置信度 | 只写描述字段，不改分数；无证据输出"证据不足" |
| `build_profile_draft` | 确定性分、描述、证据 | 画像草稿 | 每条结论必须绑定 `evidence_id` |
| `review_gate` | 画像草稿、待确认项 | `agent_interrupt` | 高影响结论必须人工确认 |
| `publish_profile` | 已确认草稿 | 发布快照、审计记录 | 发布前再次校验状态与证据完整性 |
| `trigger_reindex` | 已发布快照 | 重索引结果 | 幂等，可补偿，失败记哨兵 + 审计 |
| `emit_outbox` | 已发布快照 | `outbox_event` | 与发布同事务写入，失败则回滚发布 |

Agent 状态机（复用现状，不新增）：

```text
queued -> running -> waiting_human -> running -> success
running / waiting_human -> failed
```

`business_key = talent_profile:{talent_id}` 用于同一人才的画像任务幂等。

## 8. 接口与页面基线

### 8.1 接口编号与继承

主平台接口占用 `API-01 ~ API-95`，测评 Agent 占用 `API-096 ~ API-159`。本期画像接口从 **API-160** 起连续编号，一个接口对应一个编号，不合并、不跳号：

| 接口组 | 编号 | 用途 |
| --- | --- | --- |
| 维度与配置 | API-160 ~ API-165 | 维度列表、详情、创建、编辑、启停；配置版本读取与发布 |
| 画像生成 | API-166 ~ API-169 | 手动重算、批量重算、重算进度、Agent 运行详情 |
| 画像查询 | API-170 ~ API-173 | 画像详情、维度分、雷达数据、来源覆盖 |
| 版本与对比 | API-174 ~ API-176 | 版本历史、时间点回溯、版本对比、差异归因 |
| 证据 | API-177 | 证据清单与下钻 |
| 复核与发布 | API-178 ~ API-180 | 待确认项、提交复核、发布、回退、导出 |
| Agent 回放 | API-181 | 画像 Agent 步骤回放 |

**继承既有契约**：主平台接口文档已定义 `GET /talents/{id}/profile`（**API-34 数字画像**），前端已按该契约实现（`frontend/src/api/talent.ts`，当前因后端未就绪使用 `TALENT_MASTER_API_READY=false` 提示条）。本期画像智能体**承接 API-34 的实现**，并将其返回结构升级为本文档 §5 的画像快照（含 `dimensions` 雷达数据、`version_no`、`evidence`、`source_coverage`），**保持路径与既有前端类型兼容**。

统一遵循现有 API 约定：`code == 0` 才是成功；所有 ID 以字符串传输（雪花 ID 严禁作为 JSON number）；租户 / 组织 / 本人范围不接受前端伪造；写接口支持 `Idempotency-Key`；状态冲突使用 `40902`；非法状态流转使用 `42201`；无权限使用 `40301`；资源不可见使用 `40401`。

典型接口：

```text
GET  /api/v1/talents/{talent_id}/profile                         # API-34（承接）/ API-170
GET  /api/v1/talents/{talent_id}/profile/versions                # API-174
GET  /api/v1/talents/{talent_id}/profile/compare                 # API-176
POST /api/v1/profiles/recompute                                  # API-167
POST /api/v1/profiles/{snapshot_id}/reviews                      # API-179
POST /api/v1/profiles/{snapshot_id}/publish                      # API-180
```

### 8.2 原型页面

本期原型制作 3 个页面，沿用现有 `prototype/p01~p19` 的视觉令牌与侧栏结构；主平台页面编号已占用至 P-20，测评占用 P-21~P-26：

| 原型编号 | 页面 | 主要用户 | 核心区域 |
| --- | --- | --- | --- |
| P-27 | 人才画像工作台 | ADM/HR | 画像列表、来源覆盖、状态筛选、批量重算、待复核入口 |
| P-28 | 画像详情与版本对比 | ADM/HR/MGR/EMP | 雷达图、维度分与等级、证据下钻、版本历史、差异归因、发布状态 |
| P-29 | 画像维度与配置 | ADM | 维度列表、权重配置、等级规则、来源开关、配置版本 |

通用状态为 `loading / empty / error / forbidden / conflict`，仅按页面适用性覆盖；画像业务状态（`draft` / `computing` / `evidence_incomplete` / `waiting_review` / `published` / `superseded`）单独定义。EMP 视角复用现有 `/my/profile`（P-16）页面并接入真实画像接口。

## 9. 验收标准

### 9.1 业务正确性

- 同一 `talent_id` + 同一配置版本，画像维度分可重复计算得到相同结果，计算过程不调用模型。
- 来源缺失显式标记 `source_missing`，不得以 0 分顶替。
- 画像描述中的每条结论至少有稳定 `evidence_id`；缺证据的画像不能发布。
- 发布后的画像快照、维度分、证据不可覆盖；新版本发布后旧版标记 `superseded` 且仍可查。
- 画像不下写、不覆盖 `talent_base` / `talent_skill` / `assessment_score` 等事实来源。
- 测评报告发布事件重复投递不产生第二个画像版本（幂等）。

### 9.2 安全与合规

- `ADM/HR/MGR/EMP/AIOPS/AUDIT` 按角色和组织范围访问数据；EMP 只能查看本人已发布画像。
- 跨租户 / 跨组织 / 查看他人画像返回统一权限错误（`40301`），资源不可见返回 `40401`。
- 模型调用经过脱敏链路，画像上下文不含明文 PII；导出不含明文身份信息。
- 画像任务、步骤、AI 调用、业务审计四类记录可通过 `trace_id` / `task_id` / `business_key` 串联回放。

### 9.3 非功能

- 画像列表与详情接口 P95 小于 500ms（不含模型调用）。
- 单人人像确定性聚合 P95 小于 2s。
- 模型超时不影响确定性维度分；失败节点可重试，重试耗尽进入人工队列并告警。

## 11. 与现有项目的对齐结论（集成契约）

本智能体**可独立开发**，通过以下**三类受控接口**与既有系统集成，从而保证"顺利合并"：

| 集成面 | 契约 | 独立开发保证 |
| --- | --- | --- |
| **Agent 基座** | 复用 `agent_task`（`task_type='profile'`）/ `agent_step` / `agent_interrupt`，不新增状态机 | 图定义独立文件（`agents/profile_graph.py`），仅调用既有运行时协议 |
| **数据只读** | 只读 `talent_base` / 履历明细 / `talent_tag_rel` / `assessment_score` / `assessment_report` / `talent_change_log` | 通过各自域的只读 DAO 方法访问，**禁止跨模块直连 ORM 行对象**（承接铁律 14） |
| **事件** | 消费 `outbox_event`（档案变更 / 测评报告发布）；发布画像写 `outbox_event` | 事件类型与负载为约定常量，幂等键固定 |
| **模型与脱敏** | 复用 `core/model_gateway.py` + 脱敏链路 + `ai_call_log` | 不新建模型网关，不新增脱敏实现 |
| **前端** | 复用 `AppLayout`、设计令牌、Element Plus、权限路由、统一响应处理 | 新增独立 `views/profile/*` + `api/profile.ts`，路由独立挂载 |

工程约束：

1. 新模块按现有六层结构放置：`models/profile.py`、`schemas/profile.py`、`dao/profile_dao.py`、`services/profile_*.py`、`agents/profile_graph.py`、`routers/profile_router.py`、`alembic/versions/<profile_migration>.py`。
2. 迁移**可单独回滚**；表前缀独立，不改动既有表结构。
3. 新增测试文件必须同步登记 `tests/test_layering.py` 的 `MODULE_FILES` 与测试文档 §2.1（S-08 对账）；凡改动 Router / `core` / 新模块，针对性复跑**必带 `test_layering.py`**。
4. 遵循六层依赖只向下：`routers → services(agents) → dao → models`，`core` 横切；业务判定在 Service；DAO 纯 CRUD 且每查询必带 `tenant_id` + `is_deleted`。
5. 确定性结论来自确定性组件；LLM 只产文本。
6. 不可逆动作（发布 / 替代）幂等；已发布再发布 → 返回成功不 raise。
