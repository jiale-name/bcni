## 2. 评审方法与过程

### 2.1 五向对齐检查法（本轮主要方法）

单一模块交付时，最容易出的问题是"功能点改了，其他地方没跟着改"。因此对一期每个功能点，检查它在五个层面是否都到位：

| 层面 | 载体 | 缺失后果 |
| :-: | --- | --- |
| ① 功能点表 | §4.x | 无需求 |
| ② 权限矩阵 | §3.2 | 无权限归属 → 实现时无依据，越权风险 |
| ③ 数据模型 | §9.2.1 / §9.3 | 无字段定义 → 详细设计无法出 DDL |
| ④ 里程碑任务 | §12.1 | 无人开发、无交付物 |
| ⑤ 验收项 | §12.3 / §6.2 | 无法验收 |

### 2.2 交叉核对项

| 检查 | 方法 | 结果 |
| --- | --- | --- |
| 功能点 ↔ 权限矩阵 | 逐条比对 §4.3 与 §3.2 | ❌ 3 项缺失（→ H-14） |
| 功能点 ↔ 数据模型 | 逐条比对 §9.2.1 与 §9.3 | ❌ 倒挂（→ H-12） |
| 功能点 ↔ 里程碑 | 逐条比对 §4.3 与 §12.1 | ✅ 通过 |
| 功能点 ↔ 验收项 | 逐条比对 §4.3 与 §12.3 | ⚠️ 粒度不对齐（→ M-16） |
| **技术栈 ↔ 出网边界** | §0.3 技术栈裁剪表 与 §10.5 出网边界表 | 🔴 **直接矛盾**（→ B-7） |
| 架构描述 ↔ 一期方案 | §7.2 职责表、§8.4 链路图 与 D-13 范围 | ❌ 残留未更新（→ B-6 / H-13 / H-20） |
| 合规义务 ↔ 功能点 | §11.1 法定义务 与 §4.3 功能点 | ❌ 未落地（→ H-16） |
| 风险表 ↔ 交付阶段 | §11.2 与 D-13 | ⚠️ 未标阶段（→ M-12） |

### 2.3 场景走查

按 §2.4 的四个场景反推：S-1（简历入库）、S-3（制度问答）属一期；**S-2（领导问数）、S-4（测评闭环）已后移**。v1.2 未同步标注场景归属 → 已并入 M-17。

## 3. 本轮评审结论

### 3.1 总体结论：**不通过**

需求分析文档 v1.2 的范围收敛方向正确，一期边界清晰、技术栈裁剪干净、「无需新增中间件」这一结论对项目落地有实质价值。但复审发现 **24 项问题**，其中 **3 项阻断**，且 **B-7 是一期交付范围内的直接技术矛盾**——按 §0.3 一期要用云端模型做档案 RAG 问答，按 §10.5 简历原文不得出网，两者不可能同时成立。

**在这 3 项阻断问题关闭前，不应启动详细设计**——B-6 与 B-7 会直接决定 RAG 链路的实现形态与数据流设计，B-8 会决定 Milvus 检索接口的签名与索引设计，都是详细设计的输入。
