### 0.2 需求效力分级

原文存在大量"必须""强制""禁止"等强约束措辞。为避免把**营销型措辞**误当成**可验收约束**，本文档对原文条目做效力分级：

| 效力级别 | 含义 | 处理方式 | 原文典型措辞 |
| --- | --- | --- | --- |
| **A · 硬约束** | 客户明确指定、不可替代，违约即废标 | 全文保留，逐条落到功能点 | "强制技术栈清单（必须全部落地）" |
| **B · 目标值** | 意图明确但表述不可测，需重写为可测口径 | 本文档给出建议口径，进 §6 应答表 | "检索准确率≥95%" |
| **C · 愿景表述** | 技术上限承诺，无法保证 | 降级为可达指标 + 免责边界 | "杜绝幻觉""无人化" |
| **D · 表述有误** | 与技术事实冲突 | 标注矛盾并提出修正建议 | "PgSQL 存储时序数据""禁止裸SQL" |

> **原则**：A 类照做，B 类改写成可测口径后再签，C 类必须换表述再入合同，D 类必须书面澄清。**这四类不分清，验收阶段必然扯皮。**

### 0.4 术语表

| 术语 | 缩写 | 定义 |
| --- | --- | --- |
| 检索增强生成 | RAG | 先检索私有知识再交给大模型生成答案的范式，用于抑制幻觉 |
| 智能体 | Agent | 具备目标、记忆、工具调用与状态流转的自主执行单元 |
| 有状态工作流 | Graph / StateGraph | LangGraph 中的图式编排，节点=动作，边=条件分支，可持久化状态 |
| 自然语言转 SQL | NL2SQL | 把自然语言问题编译为可执行 SQL 的解析过程，**本质是生成 SQL** |
| 向量嵌入 | Embedding | 把文本映射到高维向量空间的稠密表示，用于语义相似度计算 |
| 分块 | Chunk | 文档切分后的最小检索单元 |
| 重排 | Rerank | 召回后二次精排，用交叉编码器提升 Top-k 相关性 |
| 上下文精度 | Recall@k | 前 k 条召回结果中包含金标准答案的比例，**"准确率"必须落到这个口径才可测** |
| 技能组件 | Skill | 可插拔、可编排的最小能力单元 |
| 服务端推送 | SSE | Server-Sent Events，用于大模型流式输出 |
| 对象关系映射 | ORM | 以对象方式操作数据库，屏蔽 SQL，本文档作为写入路径的唯一事实来源 |
| 基于角色的访问控制 | RBAC | 角色-权限模型，本文档扩展为「功能权限 + 数据权限 + 字段权限」三层 |
| 行级权限 | RLS | 同一张表按数据归属行过滤，如业务经理仅见本部门 |
| 金标准 | Gold Standard | 人工标注的标准答案集，用于计算任何"准确率"指标 |
| 分位延迟 | P95 / P99 | 95%/99% 请求的延迟上界，**比"平均响应≤1s"更能反映真实体验** |
| 语义层 | Semantic Layer | 面向分析的**受控数据库视图集合**，屏蔽物理表结构、预置行级权限条件，是 NL2SQL 唯一允许访问的对象 |
| 数据域 | Data Domain | 知识库与数据的权限分区，本平台分员工域 / HR 域 / 决策域，一文档可按分块跨域 |
| 受控词表 | Controlled Vocabulary | 只允许从预定义集合中取值的标签字典，禁止模型自由造词，用于保证统计口径可复现 |
| 倒数排序融合 | RRF | Reciprocal Rank Fusion，多路召回结果的融合算法，按排名而非分数融合，无需分数归一 |
| 分层可导航小世界 | HNSW | 一种近邻检索图索引，Milvus 常用索引类型，以内存换召回速度 |
| 检查点 | Checkpointer | LangGraph 的状态持久化机制，把工作流状态写入数据库，支撑中断恢复与人工介入 |
| 幂等键 | Idempotent Key | 保证同一业务操作重复执行不产生重复数据的唯一标识 |
| 变更数据捕获 | CDC | Change Data Capture，从数据库日志实时捕获变更并同步到下游，用于 MySQL → PgSQL 同步 |
| 外部数据包装器 | FDW | Foreign Data Wrapper，PgSQL 特性，可将外部数据源映射为本地表 |
| 人机协同 | HITL | Human-in-the-Loop，AI 产出结论前必须经人工确认方可生效的流程设计 |
| 嵌入模型 | Embedding Model | 把文本映射为向量的模型，本平台用 `bge-m3`（本地 Ollama） |
| 精排模型 | Reranker | 对召回结果二次排序的交叉编码器，本平台用 `bge-reranker-v2-m3` |
| 向量集合 | Collection | Milvus 中逻辑等价的表，一期为 `resume_vec` / `skill_vec` / `project_vec` |
| 混合检索 | Hybrid Search | 向量（Dense）召回 + 关键词（BM25/Sparse）召回融合，提升语义与字面双覆盖 |
| 受控词表审核流 | — | AI 只能从标签字典中选标签；需新增标签时走"AI 建议 → 管理员审核 → 入库" |
| 占位符回填 | Placeholder Re-hydration | 出网前把姓名/电话等替换为 `{{CANDIDATE}}`，模型返回后**在本地**还原为真值（关闭 B-7 的核心机制） |
| 检索单元脱敏 | — | 索引与检索只使用脱敏后的文本，使向量库本身不含明文身份信息 |

### 1.4 需求矛盾清单（必须澄清项）🔴

原文存在 **7 处**技术矛盾或事实性错误。这些不是措辞问题，**会直接导致架构无法落地或验收无法通过**，必须在需求评审阶段闭环。

| 编号 | 原文表述 | 矛盾点 | 建议处置 |
| --- | --- | --- | --- |
| **M-1** 🔴 | 第五章"严格禁止编写裸 SQL，所有数据增删改查均通过 ORM 实现" vs 第三章"Vanna.ai 自然语言转 SQL、自动生成标准 SQL" | **直接互斥**。NL2SQL 的本质就是让模型生成 SQL 文本并执行，不可能同时满足"禁止裸 SQL" | 表述修正为：**写入路径**强制 ORM，**只读分析路径**允许 Vanna 生成 SQL，但必须经 SQL 安全网关（只读账号 + AST 校验 + 白名单表 + 强制 LIMIT + 超时 + 审计）。详见 §10.3 |
| **M-2** 🔴 | "全程自动化无需人工干预""实现无人化业务运转" | 涉及测评结论、能力评级、人才等级调整等**影响个人权益**的动作，无人化在合规与问责上不可接受 | 改为 **Human-in-the-loop**：AI 生成建议 → 人工确认 → 生效。LangGraph 的 `interrupt` 节点落地 |
| **M-3** 🔴 | "杜绝幻觉""检索准确率≥95%""解析准确率≥99%" | LLM 本质为概率生成，无法数学保证 100% 无幻觉；指标无定义（分母是什么？Top-k？字段级？） | 拆为可测指标：**引用可溯源率 100%**（每条答案必带出处）、**无答案兜底率 100%**、**Recall@10 ≥ 阈值**（金标准集）。详见 §6 |
| **M-4** 🟠 | "十亿级向量存储、毫秒级检索"+ "向量检索响应时长≤500ms" + "≥2000 人同时在线" | 三者与单机/小规模部署矛盾。十亿级向量需分片集群，2000 并发需压测验证，不能仅靠声明 | 明确**可测边界**：一期按 100 万级向量 / 200 并发设计并实测，指标写成 `P95 ≤ 500ms @ 100万向量 / 200 并发`，扩容路径单列 |
| **M-5** 🟠 | "PgSQL 存储时序行为数据" | PgSQL 是关系型数据库，非时序库。原生分区表在海量时序写入下性能有限 | 二选一：① 引入 TimescaleDB 扩展（PgSQL 生态内，改动小，**推荐**）；② 明确"时序"实为按日聚合的宽表，非原始事件流。详见 §9 数据模型 |
| **M-6** 🟠 | "Dify 作为平台 AI 能力统一中台底座" | Dify 社区版许可对**多租户 SaaS 化商用**有限制；且 Dify 的中台能力（模型网关、应用发布）与 LangGraph 编排在职责上有重叠 | 定位收敛：**Dify = 模型网关 + Prompt 管理 + 知识库运维 + 应用发布**；**LangGraph = 复杂有状态 Agent 编排**。二者边界见 §7 方案 C |
| **M-7** 🟡 | "国产化适配：支持国产操作系统、国产服务器、国产数据库部署" | Milvus / LangGraph / Vanna.ai 在国产 OS + 国产 CPU（鲲鹏/飞腾/龙芯）上的生态成熟度参差；且 OpenAI 兼容接口的国产大模型对 Function Calling / 结构化输出支持不一 | 需甲方明确**国产化清单**（具体 OS/CPU/数据库型号），并单列适配验证任务。见 Q-3 |

### 2.4 核心场景故事

**场景 S-1 · 批量简历入库（P-2 李经理）· ✅ 一期**

> 对应功能点：F-3.1 / F-3.2 / F-3.3 / F-3.8 / F-A0（关闭 M-17 的场景标注）

李经理拿到 300 份 PDF/Word/图片简历，一次性上传。系统调用档案解析 Agent：格式识别 → OCR（图片件）→ 字段抽取 → 标准化 → 缺失字段标记 → Embedding 入 Milvus → 查重比对 → 生成画像标签。**全程自动但非无人**：解析置信度低于阈值的字段进入"待复核队列"，李经理在人工复核工作台批量确认。最终产出结构化档案 + 解析质量报告（字段级准确率、待复核清单）。

**场景 S-2 · 领导问数（P-1 张主任）· ⏸ 后续（F-5）**

张主任输入："统计本年度本科及以上青年人才占比、各部门技能人才分布情况"。NL2SQL 链路：语义解析 → 生成 SQL → SQL 安全网关校验（只读 + 白名单表 + 强制 LIMIT 1000 + 30s 超时）→ 执行 → 数据解读 → 自动出图。张主任可下钻、切换图表类型、一键导出 Word 报告。

**场景 S-3 · 制度问答（P-4 小陈）· ⏸ 后续（F-2）**

小陈问："我入职满一年能休多少天年假？"RAG 链路：问题改写 → 混合检索（向量 + BM25）→ Rerank → 权限过滤（仅返回员工可读制度）→ 生成答案 → **附引用出处**（《员工休假管理办法》第 12 条第 3 款）。若无匹配内容，系统返回"未在知识库中找到依据，请联系 HR"，**不编造**。

**场景 S-4 · 测评闭环（P-2 李经理 + P-4 小陈）· ⏸ 后续（F-4）**

HR 下发测评任务 → Agent 自动匹配试卷（按岗位层级 + 专业方向）→ 推送通知 → 在线作答（切屏/粘贴监控）→ 提交 → 自动评分（客观题确定性评分，主观题 LLM 初评 + 人工复核）→ 生成能力雷达图与研判报告 → 结论进入人才画像。

**场景 S-5 · 语义找人与档案问答（P-3 王经理）· ✅ 一期（新增）**

王经理输入"找擅长数字化转型、3 年以上 AI 项目经验的骨干"。系统做 **Milvus 混合检索（向量 + BM25）+ Rerank 精排**，检索时携带 `tenant_id + org_id` 元数据过滤（**权限前置**），返回候选人列表并附命中理由。王经理点开某位候选人档案追问"他的核心优势与短板是什么"，系统进入**档案 RAG 问答**：

1. 检索该档案的相关片段（脱敏后的检索单元）
2. **对片段做 NER 脱敏**，姓名/电话替换为 `{{CANDIDATE}}` / `{{PHONE}}`，送云端大模型生成
3. 模型逐条引用占位符片段作答
4. **本地回填**占位符为真名，返回前端展示
5. 无检索依据时直接返回"档案中未找到依据"，不编造

> 对应功能点：F-3.6 / F-3.7 / **F-3.9（脱敏回填）** / F-3.10（若追溯画像变更）

### 3.3 数据权限隔离规则

| 层级 | 规则 | 落地方式 |
| --- | --- | --- |
| **功能权限** | 能否调用某接口 | RBAC 角色-权限绑定，网关层拦截 |
| **数据行级** | 能看见哪些行 | 数据归属字段（`org_id` / `owner_user_id`）+ ORM 全局 QueryFilter 自动注入，**不依赖各接口手写条件** |
| **数据字段级** | 能看见哪些列 | 序列化层字段裁剪，敏感列（身份证、手机号、薪资）按角色脱敏 |
| **向量检索级** | 能检索到哪些向量 | **Milvus 检索前置元数据过滤**（`org_id in [...]`），禁止先检索后过滤 |
| **NL2SQL 级** | 生成的 SQL 能碰哪些表/列 | SQL 安全网关：表白名单 + 列黑名单 + 强制拼接行级条件 |
| **知识库级** | 能问到哪些制度 | 知识库分域（员工域 / HR 域 / 决策域），检索时按角色限定 collection 或 filter |

> 🔴 **红线**：向量检索与 NL2SQL 的权限必须在**检索前**生效，不能"先召回全量再过滤"——后者会把无权数据放入大模型上下文，构成数据越权。

### 6.1 基线压测先行原则 🔴（关闭 H-11）

上表的指标是**建议承诺值**，但**不是基于当前环境实测能力的推导值**。为避免"承诺与能力脱节、M7 压测不过关时无回旋余地"，确立以下强制流程：

| 阶段 | 动作 | 产出 | 若结果不达标怎么办 |
| --- | --- | --- | --- |
| N0（必做） | **基线压测**：① 现有 Milvus 在 100 万向量规模下的检索延迟与 QPS；② Redis 读写吞吐；③ MySQL 在目标表规模下的复杂查询耗时；④ 本地 Ollama 的 Embedding 吞吐（份/分钟，`bge-m3`）与字段抽取耗时；⑤ **Reranker（`bge-reranker-v2-m3`）单次精排延迟**；⑥ 云 GPU 通道的网络往返延迟 | **基线压测报告** | — |
| N0 | 用实测基线**反推**可承诺指标，与本表逐条对照 | 指标承诺表（修订版） | 若实测低于建议值：**在 N0 阶段就提出降级或追加算力**，不得拖到 N6 |
| N6 | 全链路压测验证 | 压测报告 | 未达标则按 NFR-2 的四要素定位瓶颈并整改 |

> **一句话**：先测出能力，再承诺指标；而不是先承诺指标，再赌能测过。

### 8.3 四库职责与选型

| 存储 | 版本建议 | 存什么 | 不存什么 | 关键配置 |

> **D-5 落地说明（关闭 B-1）**：原文要求 NL2SQL 可查询 MySQL 与 PgSQL。但二者是独立实例，**一条 SQL 无法跨实例执行**，SQL 安全网关也无法改写跨库语句。因此确立：**MySQL 为业务主库（唯一写入源），PgSQL 为分析副本（只读）**，业务主数据经 CDC 同步至 PgSQL。
> 由此 **NL2SQL 只面向 PgSQL 单一库**，安全网关只需维护一套表白名单与权限注入规则，链路最短、最可控。代价是引入同步链路与 ≤5s 的分析延迟（可接受：分析场景不要求实时一致）。

> 🔴 **v1.2 修订**：D-5 与本节四库设计的**完整形态适用于 F-5 NL2SQL 落地时**。v1.2 一期（档案与画像模块）**不启用 PgSQL、TimescaleDB 与 CDC 同步链路**——一期数据量级（人才主档 3.8 万、履历 80 万）由 MySQL 完全承载，向量走 Milvus，缓存走 Redis。
> 因此 **B-1（跨库 SQL）与 B-2（语义层视图）随 F-5 后移，降级为后续阶段待决项**，不再阻塞一期。本节内容保留，作为 F-5 启动时的设计基线。

> **M-5 处置**：原文要求 PgSQL 存"时序数据"。建议在 PgSQL 内启用 **TimescaleDB 扩展**（同一数据库实例，改造量小、生态兼容），而非变更数据库选型。

#### 9.1.1 多租户预留（D-10，关闭 H-9）

| 项 | 结论 |
| --- | --- |
| 一期形态 | **单租户多组织**——一套系统服务一个单位，单位内按 `org_id` 做组织隔离 |
| 是否预留多租户 | **预留**。所有业务表增加 `tenant_id` 字段，一期固定写入单租户值；权限逻辑（QueryFilter、Milvus 元数据过滤、视图行级条件）统一以 `tenant_id + org_id` 为过滤基础 |
| 预留成本 | 约 1 人天（建表规范 + 全局过滤器 + 索引调整） |
| 不预留的后果 | 后期需全表 DDL 迁移 + 全部权限逻辑重写 + Milvus 集合重建，且存量数据回填存在风险 |
| 唯一约束影响 | 所有唯一约束需从 `uk_xxx` 改为 `uk_tenant_xxx(tenant_id, xxx)` |

> 该决策的**代价是极低的**（1 人天），而**收益是消除一个高成本的结构性风险**。政企集团客户提多租户需求是常见情形。

### 9.4 语义层视图规范 🔴（D-6，关闭 B-2）· ⏸ F-5 阶段启用

> 🔴 **v1.2 状态**：本节规范**随 F-5（NL2SQL）后移**。一期不做 NL2SQL，因此无语义层视图需求——**B-2 评审问题在同一期自然消解**。本节内容保留作为 F-5 启动时的设计基线。

**为什么需要语义层**：NL2SQL 由模型生成 SQL，若允许直连物理表，则表结构变化、敏感列、行级权限三件事全部失控。语义层是"模型只看得懂的受控面"，是安全网关与权限注入的落脚点。

| 项 | 规范 |
| --- | --- |
| **命名** | `v_<域>_<主题>`，如 `v_talent_analysis`、`v_assessment_summary`、`v_org_stat`。禁止无前缀视图 |
| **物理位置** | PgSQL 分析副本（D-5 后 NL2SQL 单一数据源） |
| **生成方式** 🔴 | **由 ORM 模型单向生成 DDL，纳入 Alembic 迁移链**，与应用代码同版本发布。禁止人工在数据库侧手改视图 |
| **暴露范围** | 仅暴露**已脱敏、已聚合或已授权**的字段；身份证、手机号、薪资等敏感列**不得出现在任何视图中** |
| **权限注入点** | 视图内**预置** `tenant_id` 与 `org_id` 过滤占位；运行时由安全网关追加具体条件（不做字符串拼接，使用参数化） |
| **数量控制** | 一期控制在 **30 个以内**，按主题聚合而非按表逐一映射，避免视图爆炸 |
| **漂移检测** 🔴 | 每日定时任务比对视图定义与 ORM 模型元数据，差异即告警；纳入监控看板 |
| **变更流程** | 视图变更 = 代码变更：改 ORM 模型 → 生成迁移 → Code Review → 发布。**不允许热修** |

**视图分层**

```text
物理表（PgSQL 分析副本）
   │  ORM 模型定义（单一事实来源）
   ▼
主题视图 v_talent_analysis / v_assessment_summary / v_org_stat ...
   │  Vanna 仅能生成对这些视图的 SELECT
   ▼
SQL 安全网关（AST 校验 → 表白名单 → 敏感列黑名单 → 行级条件注入 → LIMIT + 超时）
   ▼
执行 → 结果 → 自动出图 → 解读
```

> **红线**：视图清单是**唯一允许被 NL2SQL 访问的对象集合**。新增视图必须走代码变更流程，这既是安全边界，也是"视图不会漂移"的机制保证。

## 10. 关键能力设计

### 10.1 确定性能力 vs 生成式能力边界 🔴

**这是整个平台最核心的设计原则**：凡是影响个人权益、需要审计问责、必须精确的数值，**一律不得由大模型生成**。

> 🔴 **v1.3 修订（关闭 M-15）**：增加「阶段」列，后续模块专属项标 ⏸；**补齐一期新增的 3 条确定性约束**（受控词表、查重阈值、置信度阈值）。

| 能力 | 归属 | 阶段 | 实现方式 | 理由 |
| --- | --- | :-: | --- | --- |
| Token 成本统计 | **确定性** | 一期 | 按 token 数与单价计费 | 财务口径 |
| 权限判定 | **确定性** | 一期 | RBAC 规则引擎 | 不可由模型决定 |
| 命中/命中率等指标 | **确定性** | 一期 | 埋点统计 | 验收依据 |
| **标签取值** 🔴 | **确定性** | **一期** | **只能取自受控词表 `talent_tag_dict` 的启用项**（AI 不得自由造词，需新增走"建议→审核→入库"） | 保证按标签做的统计与筛选可复现（F-3.4.1） |
| **查重阈值判定** 🔴 | **确定性** | **一期** | **相似度与阈值比对**，是否判为重复由规则决定，不由模型决定（模型仅产出相似度与命中字段） | 合并是高风险不可逆操作，阈值必须可复现（F-3.5） |
| **置信度阈值判定** 🔴 | **确定性** | **一期** | **置信度与阈值比对**决定字段是否进入复核队列（阈值可配） | 分层复核漏斗（D-8）的客观依据，不可由模型"感觉"决定 |
| 简历字段抽取 | 生成式 + 校验 | 一期 | LLM 抽取 + 字典值归一 + 置信度 | 需复核兜底 |
| 档案问答生成 | 生成式 + 引用约束 | 一期 | LLM 基于脱敏检索片段 + 强制逐条引用 + 无依据兜底 | 不得编造未在档案出现的信息（F-3.7） |
| 测评客观题评分 | **确定性** | ⏸ F-4 | 规则引擎比对答案 | 分数必须精确可复核 |
| 测评维度得分/总分 | **确定性** | ⏸ F-4 | 加权公式计算 | 同上 |
| 能力研判结论 | 生成式 + 复核 | ⏸ F-4 | LLM + 人工确认 | 影响个人评价 |
| SQL 安全校验 | **确定性** | ⏸ F-5 | AST 解析 + 白名单 | 安全红线 |
| 数据解读与建议 | 生成式 + 引用约束 | ⏸ F-5 | LLM 基于查询结果 | 不得编造 |
| 匹配分计算 | **确定性** | ⏸ F-6 | 向量相似度 + 加权公式 | 需可复现 |
| 匹配理由解释 | 生成式 + 引用约束 | ⏸ F-6 | LLM 基于维度得分 | 不得编造 |
| 制度问答 | 生成式 + 引用约束 | RAG + 强制引用 | 可溯源 |

> **红线**：任何进入数据库的**数值型结论**（分数、等级、评级）必须有确定性来源；大模型只能产出**文本型解释**。

### 10.2 RAG 链路参数基线（一期 · 档案域）

### 10.3 NL2SQL 与"禁止裸 SQL"的调和方案（M-1 处置）

原文的"禁止裸 SQL"与"Vanna 生成 SQL"是直接冲突的。工程上的正解是**按路径分级管控**，而非一刀切：

| 路径 | 允许 SQL？ | 管控方式 |
| --- | --- | --- |
| **写入路径**（增删改） | ❌ 禁止 | 强制 ORM；代码评审 + CI 静态检查（禁止字符串拼接 SQL） |
| **业务只读路径** | ❌ 禁止 | 强制 ORM QuerySet |
| **分析只读路径**（NL2SQL） | ✅ 允许，但受限 | 经 SQL 安全网关六重校验 |

**SQL 安全网关六重校验（F-5.2 落地细则）**：

```text
输入：模型生成的 SQL 文本 + 当前用户上下文
  ① 语法解析     → 用 sqlparse/pglast 解析为 AST，解析失败即拒绝
  ② 语句类型校验 → 仅允许 SELECT；出现 INSERT/UPDATE/DELETE/DROP/ALTER/TRUNCATE 即拒绝
  ③ 表白名单     → 仅允许访问语义层视图（v_talent_analysis 等），禁止直连物理表
  ④ 列黑名单     → 身份证、手机号、薪资等敏感列禁止出现在 SELECT 列表
  ⑤ 权限注入     → 强制在 WHERE 追加行级条件（org_id IN (...)）
  ⑥ 资源限制     → 强制追加 LIMIT 1000；设置 statement_timeout = 30s
输出：final_sql（改写后）或 reject_reason
```

配套措施：数据库连接使用**只读账号**；语义层**视图**屏蔽物理表结构；所有 SQL 与拦截记录落 `sql_query_log`。

**配套措施清单（闭环 M-1 / B-1 / B-2）**

| # | 措施 | 依据 | 落地位置 |
| :-: | --- | --- | --- |
| 1 | NL2SQL **只面向 PgSQL 单一库**（MySQL 业务数据经 CDC 同步为分析副本） | D-5 / B-1 | §8.3 |
| 2 | 语义层视图由 **ORM 模型生成并纳入 Alembic 迁移链**，禁人工手改 | D-6 / B-2 | §9.4 |
| 3 | 只读数据库账号（最小权限，仅 SELECT 视图） | M-1 | §13 人工操作清单 |
| 4 | CI 静态检查：业务代码禁止字符串拼接 SQL | M-1 | §12 里程碑 M2 |
| 5 | 每日视图漂移检测 + 告警 | B-2 | §9.4 |
| 6 | 全部 SQL 与拦截记录落 `sql_query_log`，可审计 | M-1 | §9.3 |

> **效果**：原文"数据安全"的实质诉求得到满足（写入走 ORM、分析走受控视图、全程可审计），同时让 NL2SQL 能力真正可交付。这是把矛盾需求转化为可落地方案的典型处置。

> **收益**：既满足原文"数据安全"的实质诉求，又让 NL2SQL 能力落地。这是把矛盾需求转化为可交付方案的典型处置。

### 10.4 Agent 状态机与人工介入契约

```text
                    ┌──────────────────────────────┐
   触发（定时/事件/手动/API）
        │
        ▼
   ┌─────────┐   失败重试（指数退避，≤3 次）
   │ PENDING │──────────────►┌────────┐
   └────┬────┘               │ FAILED │──► 人工处理队列 + 告警
        │                    └────────┘
        ▼
   ┌─────────┐   节点执行    ┌──────────────────────┐
   │ RUNNING │──────────────►│ WAITING_HUMAN        │
   └────┬────┘  命中 interrupt│ （待办：复核/审批）   │
        │                     └───────┬──────────────┘
        │                             │ approved / rejected
        ▼                             ▼
   ┌─────────┐◄──────────────────────┘
   │ SUCCESS │
   └─────────┘

每步写入 agent_step；状态写入 agent_task.graph_state；
进程重启后由 Checkpointer 从最后成功节点续跑。
```

**接口契约（Dify ⟷ LangGraph）· ⏸ F-2 / F-9.4 阶段启用**

> 🔴 **v1.3 标注（关闭 H-20）**：本契约是为"Dify 应用编排 ⟷ LangGraph 任务交互"设计的。**一期 Dify 只做模型网关与 Prompt 管理，不承担应用编排**，因此不存在 Dify 侧任务与 LangGraph 的 `task_id` 交互——**一期无需实现本契约**。一期只保留 Agent 状态表（`agent_task` / `agent_step` / `agent_interrupt`）与上图所示的人工介入机制。本契约在 F-2 / F-9.4 引入 Dify 应用编排时启用。

| 项 | 约定 | 阶段 |
| --- | --- | :-: |
| 任务标识 | 统一 `task_id`（雪花 ID），Dify 侧记为 `conversation_id` 的扩展字段 | ⏸ F-2 |
| 回调 | LangGraph 完成后回调 `${APP_BASE}/internal/agent/callback`，带 `task_id` / `status` / `result_ref` | ⏸ F-2 |
| 鉴权 | 内部调用使用固定 `INTERNAL_TOKEN`，不走用户鉴权 | ⏸ F-2 |
| 大结果 | 结果不内联，存对象存储/DB，回调只传引用 | ⏸ F-2 |
| 幂等 | 回调接口按 `task_id` 幂等 | ⏸ F-2 |

**记忆与状态的职责边界 🔴（关闭 M-2）**

Redis 与 PgSQL 都会承载"记忆"，若不划清边界会出现"以为存住了其实丢了"的隐性故障。

| 维度 | Redis（短期热记忆） | PgSQL Checkpointer（权威状态） |
| --- | --- | --- |
| 存什么 | 会话上下文、本轮对话消息、临时中间结果、模型调用缓存 | Agent 图状态、已完成节点、重试计数、人工介入待办 |
| 是否可丢 | ✅ **可丢**（TTL 过期或 Redis 重启不影响正确性） | ❌ **不可丢**，丢了任务无法续跑 |
| 生命周期 | 会话级，TTL 默认 2 小时 | 任务级，保留 ≥6 个月（符合审计要求） |
| 冷启动 | Redis 未命中时**从 PgSQL 重建**会话上下文 | — |
| 写入顺序 | 先写 PgSQL，再写 Redis（**PgSQL 为准**） | 唯一事实来源 |
| 禁止事项 | ❌ 任何关键状态**不得仅存于 Redis** | ❌ 不得把大文本中间结果写入状态字段（用引用） |

> **判定口诀**：**"丢了会不会做错？会 → 落 PgSQL。不会 → 放 Redis。"**

### 10.5 混合算力路由表与出网边界（D-4 落地）

> 🔴 **v1.3 重写（关闭 B-7）**：v1.2 存在直接矛盾——§0.3 要求"档案 RAG 问答用云端模型"，§10.5 又要求"简历原文不出网"。v1.3 通过 **D-15「检索单元脱敏 + 占位符本地回填」** 调和：**出网的从来不是简历原文，而是脱敏后的检索片段（身份信息已替换为占位符）**，模型基于占位符生成，返回后在本地回填真值。这是唯一同时满足"云端模型质量"与"数据不出网"的方案。

### D.1 推荐开发顺序

> 🔴 **估算假设（关闭 L-7）**：下表工期为**按 4~5 人团队**（同 §15.1：技术负责人兼架构 1、后端 1~2、AI 工程师 2、前端 1、测试 0.5~1）的**单模块独立开发**估算，不含跨模块联调与甲方决策等待时间；与一期 §15 的团队假设保持一致。团队规模变化时按比例调整。

| 序 | 模块 | 建议时机 | 复用一期成果 | 需新增能力 | 估算（4~5 人） |
| :-: | --- | --- | --- | --- | :-: |
| 1 | **F-2 RAG 企业知识库问答** | 一期后立即 | LangGraph / Prompt / AI 日志 / Milvus | 文档解析与分块（可复用 F-3 解析器）、知识库分域与打标、Dify 知识库运维 | 8 ~ 12 周 |
| 2 | **F-4 AI 智能测评** | 可与 F-2 并行 | 基座全部、人才画像（出题依据） | 题库与审核状态机、任务调度、作答监控、确定性评分 | 8 ~ 11 周 |
| 3 | **F-6 岗位-人才匹配** | F-4 之后 | **向量画像与语义检索（F-3 核心资产，匹配即复用）** | 岗位结构化解析、加权匹配公式、匹配解释 | 4 ~ 6 周 |
| 4 | **F-7 智能培训** | F-4 / F-6 之后 | 能力缺口（来自 F-4）、画像（来自 F-3） | 课程库、学习计划、进度管控、复测闭环 | 6 ~ 9 周 |
| 5 | **F-5 NL2SQL 数据决策** | 独立立项 | 基座、审计体系 | **PgSQL + TimescaleDB + CDC + 语义层视图 + SQL 安全网关 + Vanna**（见 §9.4 / §10.3） | 10 ~ 14 周 |
| 6 | **F-8 Skills 编排组件库** | **最后做** | 前五个模块的全部能力 | 组件标准化封装、可视化编排画布、触发机制 | 6 ~ 9 周 |
| 7 | **F-10 多端协同** | 可按需穿插 | 全部 API | 响应式适配 / 原生 App | 3 ~ 5 周 |

### D.2 依赖关系

```text
一期 F-3（档案与画像）
   │
   ├──► F-2 RAG 知识库问答（低耦合，可独立启动）
   │
   ├──► F-4 智能测评 ──┬──► F-7 智能培训（依赖测评的能力缺口）
   │                   │
   └──► F-6 岗位匹配 ◄──┘（复用 F-3 的向量画像，最省力）

F-5 NL2SQL ──── 独立立项，与其他模块无强依赖（但需引入 PgSQL）
F-8 Skills 编排 ──── 依赖前六个模块的组件齐备，必须最后做
F-10 多端协同 ──── 依赖全部后端 API 稳定
```

### D.3 关键提醒

| 序 | 提醒 | 原因 |
| :-: | --- | --- |
| 1 | **F-6 是最划算的下一步** | 一期的向量画像与语义检索几乎是它的全部前置，边际成本最低 |
| 2 | **F-5 是最贵的一步** | 需引入 3 个新组件（PgSQL / CDC / Vanna）并重建数据访问层，建议单独立项、单独报价 |
| 3 | **F-8 必须最后做** | 组件库的价值来自"有组件可编排"；提前做只能造出空壳框架 |
| 4 | 每启动一个后续模块，**先补该模块的金标准集** | 否则指标无法验收（见 §13） |
| 5 | ⚠️ **一期接口预留建议** | 一期设计时，档案与画像的对外接口应尽量做成**标准可复用能力**（如"向量检索""字段抽取"），后续模块可直接调用，避免二次改造 |
