# 人才测评分析 Agent 数据库设计文档

> 版本：v1.0  
> 日期：2026-09-28  
> 基线：需求分析文档、架构设计文档、P-21～P-26 原型  
> 数据库：MySQL 8.x

## 1. 设计目标

本设计为 P-21～P-26 原型提供完整的持久化模型。原型中出现的题目、版本、筛选状态、试卷配置、任务、候选人进度、作答、监控事件、评分、报告、证据引用、人工复核、Agent 运行信息和审计动作都必须有可追溯的数据来源。

数据库设计遵循以下原则：

1. 发布后的题目、试卷、评分和报告只追加版本，不覆盖历史快照；TBL-36 `assessment_answer` 仅保存当前答案，不保存无限历史。
2. 所有业务表默认带 `tenant_id`；需要组织隔离的表同时带 `org_id`；如果表级字段定义明确列出完整字段集合，则以表级定义为准。
3. 所有状态变更都通过服务层完成，并写入审计日志。
4. 客观评分可重复，主观题 AI 结果只能写入建议字段，最终分必须由人工确认。
5. P-21～P-26 的列表、详情、筛选和操作接口都可以通过本设计的数据表独立实现，不依赖页面内置静态数据。

#### TBL-35～TBL-37 Attempt 契约冻结补充

以下规则是业务契约，不改变本节既有字段定义：

1. TBL-35 `assessment_attempt.status` 仅允许 `not_started`、`in_progress`、`submitted`、`auto_submitted`、`cancelled`。允许流转为 `not_started -> in_progress -> submitted`、`in_progress -> auto_submitted`、`not_started / in_progress -> cancelled`；后三个状态为终态，不得新增状态。
2. TBL-35 的 `attempt_no` 表示当前任务下候选人的第 N 次 Attempt。`assessment_task_candidate.attempt_count` 表示已创建 Attempt 数量，并作为 `attempt_limit` 的权威校验依据。创建 Attempt 时必须锁定 Candidate 行、校验次数、生成序号、原子递增次数并在同一事务中创建 Attempt。
3. TBL-35 的 `answer_version` 初始值为 `0`。保存答案时必须校验客户端版本，成功后更新同一 TBL-36 当前答案记录并将 Attempt 版本递增；首次保存版本为 `1`，后续按 `N -> N+1` 更新，版本冲突返回 `40902`。
4. TBL-35 的 `paper_snapshot` 来源于 TBL-33，在创建 Attempt 时生成；Attempt 同时在业务语义上绑定创建时任务关联的已发布 Paper `version_no`，该版本就是本次评分上下文版本；后续读取 Attempt 不得实时读取题库或当前最新 Paper 内容。本轮不改变 TBL-35 字段定义，具体承载方式留待后续实现阶段。
5. TBL-37 的 `client_event_id` 为 VARCHAR(64) NOT NULL，用于客户端事件幂等，唯一约束为 `UNIQUE (tenant_id, attempt_id, client_event_id)`，约束名为 `uk_attempt_client_event`。重复事件返回首次创建的 `event_id`，不创建新事件且不产生重复副作用。
6. Candidate 联动不得新增字段：API-131 成功开始时更新 `assignment_status=started`、`attempt_count + 1`、`progress=0`，`deadline_at` 保持任务截止时间；API-134 只更新 `progress`；API-138 更新 `assignment_status=submitted`、`progress=100`；自动交卷更新 `assignment_status=submitted`、`progress` 按最终答案计算，且 `attempt_count`、`deadline_at` 不变。

## 5. 事务、版本和迁移

1. 发布试卷必须在一个事务中完成：校验题目、写入题目快照、写入维度快照、写入规则快照、更新试卷状态、写审计。
2. 提交作答必须在一个事务中完成：锁定 Attempt、保存最终答案版本、更新提交状态、更新 Candidate、写入 `assessment.score.requested` 评分任务 Outbox 事件。Outbox 写入失败时整个事务回滚，禁止出现已提交 Attempt 无可靠评分任务记录。API-138 只能执行 `in_progress -> submitted`；`submit_after_deadline` 仅为事件类型，不参与 API-138 状态转换。
3. 发布报告必须在一个事务中完成：校验证据和人工复核、写发布快照、写审计、写入 `outbox_event` 画像同步事件；画像同步本身在事务外消费并可重试。
4. 迁移脚本必须可重复执行；上线前执行结构校验和回滚演练。
5. 删除只允许软删除草稿数据；已发布数据只允许标记为 `superseded` 或 `archived`。
6. `tenant_id`、`org_id`、资源 ID 和版本号必须同时参与服务层权限校验，不能只依赖前端传参。

### 5.1 Attempt 事务与实施顺序冻结补充

Attempt 数据层实施依赖顺序固定为：

```text
TBL-32 -> TBL-33 -> TBL-35 -> TBL-36 -> TBL-37
```

API-131 创建 Attempt、Candidate `attempt_count` 更新和快照生成必须在同一事务中完成，并锁定 Candidate 行防止并发超出 `attempt_limit`。API-138 主动提交和超时 Worker 必须通过 Attempt 行锁/状态条件保证只有一个提交结果生效。TBL-37 必须使用 `uk_attempt_client_event(tenant_id, attempt_id, client_event_id)`，`client_event_id` 为 VARCHAR(64) NOT NULL。

## 6. 数据保留和脱敏

- 作答原文、报告正文、评分说明属于敏感数据，按租户策略保留。
- 监控事件只保存摘要，禁止保存剪贴板原文、摄像头原始数据和麦克风原始数据。
- 导出文件保存文件哈希、导出人、导出时间和授权范围，不把文件路径直接暴露给客户端。
- 测试环境使用脱敏人才 ID、题干和作答内容；禁止使用真实候选人报告。
